## Sources and method

- [Machine-readable aggregate snapshot](baseline-2026-09-25.json) records page metadata, exact decimal amounts, indexed block identity/timestamp and source-code SHA-256 hashes.
- Public campaign evidence: `https://pi.soramitsu.io/graphql`, operation `TonswapBurnSnapshot`, using the repository's existing `src/indexer/queries/tonswapBurn.ts` fetch function. It fetched both pages, with 26 and 4 rows, freezing the second request to the first response's indexed block. It validated mainnet genesis, campaign start block, freshness, row amounts and identities, ordering and pagination completeness.
- Existing `allocateTonswapBurns` and `getTonswapCurrentRate` in `src/features/misc/lib/tonswapBurn.ts` performed accounting with the application's existing `FPNumber` implementation and integer reward calculations. The one-off Node invocation mapped the SDK's `FPNumber` re-export to that same repository math module; it did not change application code.
- The allocator validates transaction identity and execution position, deduplicates identical evidence, orders by block and extrinsic index, and excludes the configured SORA Trust account by public-key identity before cap/reward accounting. Zero excluded burns means zero in this complete returned campaign snapshot; it does not quantify other burns, malformed markers, failed transactions or records outside the campaign.
- Read-only finality/timestamp cross-check: `https://ws.mof.sora.org/`, using `chain_getBlockHash`, `state_getStorage` for `Timestamp.Now` at that block, `chain_getFinalizedHead`, and `chain_getHeader`. No signing or transaction submission occurred.
- Independent Python `Decimal` arithmetic confirmed the cumulative curve reward, floored to 18 decimals, and the XOR conservation/cap totals. All token calculations used exact decimal or integer arithmetic.

The indexer certifies successful finalized campaign burn evidence. The frontend parser and allocator do not independently re-execute the entire chain. The snapshot contains no pending burns, no proof of recently acquired XOR, and no evidence of immediately delivered TS or a claim being exercised.

## Using this baseline

For each follow-up, capture a fresh complete snapshot with its indexed block and timestamp, and subtract the exact included/eligible XOR, TS reservation and burn-count totals above. Report excluded and over-cap amounts separately. A comparison must retain this campaign's start block, genesis, exclusion policy, allocator version and 18-decimal accounting; if a rule changes, publish a restated baseline instead of silently mixing methods.

Keep public burn accounting separate from the [product event specification](analytics-events.md), publisher click reports and consented usability observations. A rise after a post shows a time association only. It does not establish that the post caused a burn, that a burn represents a purchase, or that funds reached the operating entity.
