# Persisted exact goal accounting

`src/features/bot-trading/goal-exact-ledger.ts` is an additive pure reducer. It does not modify the legacy `BotGoalState`, frozen historical reducers, wallets or live execution. The additive storage adapter below persists its state in the existing IndexedDB ledger. It provides accounting and admission evidence, not qualification, receipt authentication or permission to trade.

## Fixed episode and exact marks

`createGoalExactLedger(config, openingMark)` starts one funded episode. The initial KUSD amount is positive and at most 10 KUSD; a separate 1 XOR is initially held for native fees. The duration is 24 hours, the target is 5% in net XOR value, and the maximum drawdown is 5% from the observed goal peak. The KUSD order ceiling is strictly below the initial allocation. Both asset precisions are fixed at 18; input quantities and reserves are canonical u128 codec strings.

The configuration contains `goalId`, `startedAtMs`, `initialKusdCodec`, `maxTradeKusdCodec` and `maxTradeXorCodec`. A mark contains `blockHash`, `blockNumber`, `timestampMs`, `denominator`, `kusdReserveCodec` and `xorReserveCodec`. Its denominator cannot change during the episode. The caller supplies proof that it is a canonical same-state KUSD/XOR observation on the policy's SORA genesis; this module makes no RPC requests or proof-verification claim.

The opening observation may be at most 60 seconds older than the explicit funding time, and may not be in the future. Funding time is the accounting baseline; the observed block timestamp remains unchanged. Later accounting times and block lineage cannot regress. Reusing a block requires exactly identical reserves, timestamp and denomination. New blocks require a different hash. All marks must remain within the same 60-second age bound relative to the supplied accounting time.

Valuation uses the exact rational number `(netKUSD × xorReserve + netXOR × kusdReserve) / kusdReserve` in XOR codec units. Numerators and denominators are reduced integer strings. There is no floating-point token arithmetic, USD peg or rounded price. Deficits, if an actual receipt exceeds the tracked allocation, are subtracted from net value; they never disappear because holdings are clamped at zero.

The reducer privately tracks recursively frozen own-data identities to reuse canonical serialization. Every raw restore still creates a fresh bounded detached copy and performs the complete schema, checksum, ratio, settlement, fee, balance and outcome checks. External frozen objects and serialized copies remain untrusted. The cache certifies immutability only; it grants no validity, market provenance or wallet authority. The restore-only copy mode freezes each freshly constructed array or own-data record in postorder and privately admits that new identity. It preserves every raw descriptor/prototype/dense-array/size check, then performs the same full restore validation; it avoids a second descriptor/prototype traversal of the fresh output. No raw caller object is frozen or branded, and ordinary create/mark/fill/receipt copy calls retain their mutable detached defaults. This is an implementation seam, not a restore bypass or trust in a supplied checksum. It does not establish a measured speedup or passing qualification episode.

During the same full postorder restore copy, an existing canonical string may be carried from an exact privately frozen source array or record to its newly frozen detached copy. All raw descriptor, prototype, dense-array, primitive and aggregate bounds still execute before that container is admitted; this reuses only serialization bytes. Each descendant value and own string key is copied unchanged, so the copied dense array or sorted-key record has the same canonical bytes. Default mutable copies never admit identities or carry cache strings. External frozen objects, mutable sources and proxy wrappers cannot acquire the private marker merely by being read, serialized or sharing a checksum. A partially copied invalid parent's new children remain inaccessible outside the failing call and are held only by weak registries; no raw parent or child is branded/frozen. Public restore still creates fresh detached identities and performs every original checksum, receipt hash, reconstruction and economic check. This change has no measured speedup or passing qualification result until the unchanged validation gates complete.

Ledger canonical digests select the installed library's browser-compatible JavaScript SHA-256 engine with the second `sha256AsU8a` argument set to `true`. The canonical text, UTF-8 encoding and SHA-256 bytes remain unchanged. A bounded offline Node comparison found lower hashing CPU time on representative ledger body sizes; it does not establish browser or end-to-end replay performance, and every raw checksum/accounting check still runs.

## Operations

- `restoreGoalExactLedger(raw)` copies and freezes bounded own-data records, validates the schema and canonical SHA-256 checksum, and reconstructs balances, fees and trade/failure counts from retained settlements. It rejects inconsistent ratios, contradictory identifiers, malformed records, unsupported policy and corrupted derived balances. The checksum is an integrity check, not authentication: someone able to rewrite all stored fields can recompute it. Historical peaks and mark ancestry are retained claims that require trusted atomic persistence; the checksum cannot prove external market history.
- `markGoalExactLedger(state, { expectedRevision, accountingAtMs, mark })` updates observed net value and exact peak/drawdown metrics. It latches target or loss before the deadline. At or after the fixed deadline an active goal expires at the original end time, without backdating a new target/loss to an old observation. Stopped outcomes stay latched while later marks continue to describe held inventory. Such later values are not relabeled as the endpoint's value.
- `assessGoalExactFill(state, { expectedRevision, accountingAtMs, mark, fill })` first marks actual holdings, then evaluates minimum-output success and fee-only failure without saving either scenario. The fill contains `inputAsset`, `inputCodec`, `outputAsset`, `minimumOutputCodec` and `feeCeilingCodec`; assets must be the exact KUSD/XOR pair and fees are native XOR. Both hypothetical outcomes must remain strictly below 5% loss from the observed goal peak. The unspent portion of the original 1 XOR fee allowance stays protected from selling, and future output cannot fund the current input or fee. A stopped/attention state, exhausted fee allowance or full receipt log prevents new admission. Quote age, impact, route proof, slippage-minimum derivation, strategy limits and wallet authority are separate caller checks.
- `settleGoalExactLedger(state, settlement)` records an already-realized finalized receipt. It does not run admission again and discard an actual debit merely because the goal stopped or expired. The result contains `{ state, duplicate }`. Settlement adds `orderId`, `receipt`, `fill`, `success`, `actualOutputCodec` and `actualFeeCodec` to the observation fields. The receipt contains `blockHash`, `blockNumber`, `extrinsicHash` and `extrinsicIndex`. Receipt verification, account scope and binding to the reserved intent remain caller duties.

Successful settlement deducts exact input, credits actual output and charges the actual network fee once. Failure deducts only its actual fee and does not invent a successful trade. A fee above its estimate/budget, breached minimum, exceeded order ceiling, use of the protected reserve or allocation deficit produces latched attention that prevents new admission. A late receipt from a block earlier than the last observed block is recorded at the supplied current mark and flags `late-settlement`; the reducer does not invent a corrected historical peak or change a previously latched outcome. Deficits remain explicit until actual subsequent receipts offset them. No additional funding is inferred.

## Persistence and idempotence

Every mutation increments `revision` and retains `previousStateSha256`. Repeating an identical mark at the identical accounting time is a no-op. Settlements retain order identity, canonical block/index identity, extrinsic hash and a digest of their exact contents. A matching old receipt returns the current state unchanged even after reload and later revisions. Reusing any of those identities with conflicting contents rejects the write.

The log holds at most 4096 settlements. It never evicts deduplication evidence. At capacity, new admission and a new distinct settlement fail closed; repeated existing receipts remain idempotent. The storage adapter stops admission at this bound and retains an externally finalized receipt pending reconciliation rather than deleting old entries.

The reducer cannot globally revoke old immutable references. The storage adapter must atomically compare goal/session identity, expected revision and the prior state hash before committing the returned state, together with the corresponding reserved-order and finalized-receipt updates. Never overwrite it from a stale UI snapshot. The separate storage adapter implements this atomic boundary; production execution is not activated by either module.

Synthetic unit tests cover exact threshold boundaries, both fee scenarios, reserve protection, serialization/restore, stale revisions, conflicting receipt identities, old duplicates, post-stop/expiry receipts, deficits, integrity checks and the no-eviction capacity bound. They make no network calls and contain no retained market observations.

## Implemented storage boundary — no execution activation

`goal-storage.ts`, `goal-execution-types.ts` and the `createBotStorage().goals` namespace implement the exact-state corridor in the existing `polkaswap-bots-v1` IndexedDB database, `ledger` store and single `state` record. Database version 2 creates the store only when absent and preserves existing records. An old version-1 connection receives `versionchange` and closes; reopening version 1 fails with `VersionError`. A blocked upgrade fails closed rather than opening a second database.

The additive `GoalExecutionBot` has a strict `goalExecution` binding, `goalControl: { revision }`, `goalSignal: { completedAtMs }` and `exactGoalState`; `goalState` is absent. The signal boundary starts null and persists the last consumed completed hour independently of actual decision time. It does not change frozen `BotDefinition`. The binding contains protocol `finalized-xyk-goal-v1`, the separate strict two-field `execution` request, immutable `goalId`, and consent/qualification/policy digests. Digest presence does not establish consent or qualification. The exact state owns accounting; legacy portfolio fields are checked projections. Only running, paused and attention statuses are supported, and all retain allocation. There is no release, reset or deletion API for this protocol yet.

An order retains that binding, preflight accounting revision/hash, control revision, quote digest, prepared-intent envelope digest, fee-policy digest and an independent order revision. `envelopeDigest` is the canonical prepared intent envelope digest. `signedEnvelopeDigest` is the digest of actual signed bytes; neither is silently substituted for the bounded fee-envelope hash. The storage module neither signs nor verifies those bytes.

### Atomic APIs

- `initialize` receives the unfunded bot configuration, allocation limits, opening mark, balances and synchronous owned-context hook. It creates the fixed baseline at the transaction's current time and starts paused with control revision 0. Call it only at actual approved funding/allocation, never while previewing a plan. It refuses an existing bot/goal identity or supplied exact/control state. `resume` checks balances and starts an authorized session without recreating the original baseline, deadline or holdings.
- `observe` compares goal, accounting revision/hash and control revision, then commits the valid mark, exact progress and portfolio/status projection together. It refuses to value stale holdings while a finalized receipt is awaiting accounting.
- `recordSignal` additionally compares the previous consumed boundary and atomically records a new current completed hour, its causal strategy state and the fresh exact mark. Initialization requires unseeded decision/trade state. Later decision timestamps are actual accounting times; successful receipt accounting alone advances `lastTradeAt`. A repeated hour rejects even when its economic mark is unchanged. A concurrently observed target/loss stop persists with the consumed signal; no fill is implied. See the [runtime composition](bots-goal-runtime.md).
- `reserve` checks that same CAS, original order bindings, session and whole-account allocations/pending orders, then evaluates minimum-success and fee-only-failure. It commits an observed goal stop even when returning an admission rejection. Only an admitted order is appended; reservation does not debit funds.
- `sign` records actual signed-byte identity and transaction hash for the original unsigned reservation. It may record facts after a pause. `submit` is the atomic **intent-to-broadcast** gate: it requires signed status, current accounting/control CAS, the reservation's unchanged control epoch, active unexpired session/goal, no attention or unaccounted receipt, matching transaction hash and a synchronous owned-context hook. It does not prove broadcast occurred. The eventual caller must recheck its private consent capability immediately before sending. Interrupted recovery accepts a verified receipt from either signed or submitted status.
- `cancel` only cancels an unsigned reservation and retains its identity. It charges no invented fee. `pause` compares only goal/control revision, so a contemporaneous fee/mark accounting update cannot prevent a user's pause. Pause clears the session and increments control revision. Resume increments it again, preventing stale asynchronous work from crossing Pause→Resume. A status change caused by target/loss/expiry or attention also advances control revision.
- `persistFinalReceipt` retains verified finalized economic facts on the order, with a canonical receipt digest, without requiring a fresh mark or restorable exact accounting state. It validates goal/order/account/network/transaction identity and rejects conflicting receipts. Its pending status blocks further admission for the whole account but preserves existing session metadata and unrelated bots. Pending accounting is a durable settling/reconciliation state, not proof of authority revocation or an invented failure.
- `applyReceipt` uses accounting-only goal/revision/hash CAS; a later pause cannot erase an actual debit. With a fresh owned-context mark, it atomically commits the exact economic change, order status, receipt-applied identity and portfolio. Actual fees, low output, deficits and post-stop facts remain visible. A clean expected settlement preserves a still-valid session and does not undo a user pause. Actual anomalies or ended goals change status through the exact reducer. An identical old receipt returns the current state without charging again.

All caller data is copied before the first asynchronous database step using bounded own-data validation; accessors, sparse arrays and unsupported records reject. Hooks are required to be synchronous, are checked before and after protected transaction work, and reject async/thenable returns without leaking their eventual rejection. Transaction failure rolls back both bot and order changes.

Every generic mutation checks both incoming and stored records. Any own `goalExecution`, `exactGoalState`, `goalControl` or `goalSignal` marker, including undefined or unknown protocols, is rejected on legacy paths. Listing validates marked records **before** JSON projection can remove undefined markers. A malformed exact record cannot masquerade as legacy and reach its signer. Unaccounted receipts and allocation deficits block new allocations/reservations across the same account/network; zero-clamped holdings cannot conceal external debit. Dedicated receipt retention remains available without pretending a corrupted state is already reconciled.

The adapter does not authenticate market provenance, canonical receipts, qualification, consent or wallet authority. Those remain explicit caller obligations. It cannot make a database transaction atomic with a network broadcast. The new path is not activated in the production bot controller by these changes.

Synthetic unit tests cover fixed policy, initialization/resume, exact and control CAS, durable signal consumption, pending-order exclusion, observed-stop commits, protected funds, finalized overruns, corrupt accounting with retained receipt, duplicate application, accessor rejection and synchronous guard rollback. Real Chromium and WebKit IndexedDB tests use an isolated synthetic origin with all unrelated requests blocked: same-record v1→v2 migration/old-client fence, concurrent reservations, marker downgrade rejection, durable receipt reload, atomic rollback, exactly-once concurrent settlement and signal consumption, stale cross-tab Start/Pause, and stored undefined-marker reads. No wallet or live RPC is installed in these tests.

## Private own-data projection reuse

Ledger copies may reuse a private projection of own-data field values, enumerability and original own-key order only for an exact identity previously admitted by this module after recursively freezing detached data. The projection and its containers are immutable. `freeze` can retain those stable fields from the descriptors it already validated, after the freeze succeeds; writable/configurable flags are deliberately excluded because freezing changes them. Newly copied outputs never receive a source projection containing source-child references. An owned cache miss reflects once, while every raw, externally frozen, null-prototype external copy and proxy wrapper is reflected again on every copy. A proxy remains valid raw input when its current reflected shape satisfies the existing rules; it receives no private ownership.

Every copy still allocates a fresh array/record for every occurrence, checks the source prototype, key/array limits and dense own-data shape, visits every primitive and descendant, and counts every occurrence against the same node, depth and aggregate character limits. Mutable default copies stay mutable. Restore still performs the complete checksum, ratio, receipt, reconstruction and economic validation. The projection grants no semantic validity or financial authority and is never exposed through the public state. Weak sidecars live with their owned identities; additional projection allocation and retention may offset reflection savings.

The completed unchanged Node economic-rejection profile showed ledger copy stacks during producer and qualification work. Its weighted sample intervals are wall intervals, not CPU time or completed-call counts, and do not isolate descriptor reflection. The original 20-second case timed out on a heavily loaded host. This candidate establishes no measured speedup, passing deadline or completed episode; root must run the unchanged validation gates and compare actual evidence. Appended tests use selected-identity descriptor counts and fresh-result equality, untrusted external/proxy/shape rejection, and node/character/depth bounds with a later probe that must remain unvisited.

### First-use projections for restore outputs

After restore's copy has visited every child, allocated the existing fresh array/record, frozen it and privately admitted its exact identity, it seeds that output's projection. Fresh-copy projection mode reads field values only from the new output; source descriptors supply the already checked own-data kind and enumerability. It reads the actual frozen output keys once because a raw array proxy can vary its reported length between the unchanged guard and constructor reads; seeding source keys could misdescribe the actual output. It never retains a source-child reference as an output field. The constructors and all visits/limits remain unchanged, and no second descriptor reflection of the output is needed. Ordinary mutable copies do not seed projections. Full restore/hash/accounting validation still follows the initial copy.

This closes the first-use miss when the next mark copies descendants of a prior restore. The applied V2 unchanged Node case still failed its original 20-second deadline; its wall/CPU measurements on a different heavily loaded interval do not establish a speedup. The appended first-use test starts from a cold raw snapshot, mutates its original children after restore, and counts reflection on two successive fresh owned outputs without warming them. It requires fresh identity, unchanged values/checksums, and rejection of both raw and rehashed corrupted accounting. All V2 aggregate/depth/raw-shape and older semantic tests remain intact. Projection allocation and retention remain costs to measure; neither this candidate nor its static review establishes an end-to-end deadline pass.
