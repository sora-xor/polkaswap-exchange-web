# Automatic AI trading

`/#/bots` opens a beginner workflow: the ready-made bots ([bots-quant-loop.md](bots-quant-loop.md)) followed by the **AI trading** card described here. The **Advanced** link in the page header retains the existing lab, strategy composer, manual bot editor, and backtesting inspector; **My Bots** sits beside it.

The card opens with one plain sentence: choose a budget and the token to grow; the assistant (the Codex app or an API key) drafts strategies, Polkaswap tests them on past data, and the user reviews the best one before it trades. The sentence is shown only on the setup form. The primary button reads **Find a strategy**; this document calls that action GO, its original label and code name (`go`, `autopilot-go`).

Initial token discovery shows “Loading tokens…” until finalized public pool data arrives. A failed read shows “Token data unavailable. Retrying…” and uses the existing 30-second retry; the failure stays visible while that retry is pending. An accepted catalog with fewer than two tokens shows “No liquid trading pairs are available.” Recovery changes only the available token list, preserving the budget, goal limits and wallet permissions. Existing watch and qualification messages take priority over this setup status.

1. Enter a trading budget, choose its input token, choose the output token to maximize, and press **GO**. The budget is total starting capital, not an instruction to swap that amount. These controls are visible on the first screen; other settings stay collapsed. The selected output token is the unit used to measure portfolio growth and the goal. The initial goal targets a 5% increase and pauses after an observed 5% loss over one day.
2. GO preserves the submitted amount and token pair while completing missing connections. Keep the current connected wallet, or connect a supported SORA wallet when prompted. Then connect the assistant to this exact tab. Research continues automatically after these connections, without another GO or Continue action. There is no separate deposit contract: funds remain in the connected wallet. XOR capital includes its fee reserve; other capital tokens require a separate XOR fee reserve.
3. Codex uses a connection ID for this tab. Open Codex or copy its task into another assistant, keeping the wallet's browser and profile. The page waits until the assistant acknowledges the ID through WebMCP or the visible **Assistant controls**; opening a link is not a connection. The assistant receives bounded training context and can return one batch of up to three distinct deterministic strategies through site tools or ordinary browser controls. Without browser access, it can receive **Copy instructions** and return JSON for **Strategy response**. Each proposed amount and cadence is quoted exactly. The optional **Use an API key** path requests the draft directly: OpenAI and Claude discover an available model; Jev and compatible providers use the user's HTTPS relay. API credentials stay in memory. No wallet signature or bot allocation is created during research. If evidence is unavailable or no strategy qualifies, funds stay untouched.
4. Review the total trading budget and the separate maximum input per swap, both visible before the collapsed limits, then explicitly authorize the session and goal. Built-in wallets use **Unlock & start**: this unlocks a private, memory-only signer for the existing bounded executor and subsequent transactions sign automatically within that session. Extension wallets use **Authorize and start**, without requesting a password in Polkaswap; their existing signer requests approval for each trade. Connecting an assistant never changes wallet permissions or bypasses those prompts.
5. The running view shows holdings, observed goal progress, trade count, Pause and Stop. Closing or reloading the page cannot silently restore a signing key. Resume requires fresh authorization (and a new unlock for built-in wallets); it preserves the original goal baseline and deadline.

The GO form always shows its current XOR network-fee reserve beside the action: an additional reserve for non-XOR input, or an included reserve for XOR input. A partial trade requires at least two base units of spendable input. The form applies this minimum to non-XOR capital and to XOR capital after its included reserve, before GO or restoring a saved draft. Editing the reserve under Trading limits updates the note immediately. This states the required budget, not available wallet funds; the qualified review still checks transferable balances and requires explicit authorization.

Desktop opportunity watching cannot wake a desktop assistant. Its watch note asks the user to open their AI for each new check; a pending request shows the current **Open Codex** link prominently, with **Copy instructions** available when a direct link is unavailable. If the optional local Codex companion is paired, that local process can answer each new eligible hourly training request while both it and this page remain open. Opening either connection path does not approve trading. API-connected watches retain their existing automatic request behavior.

## Desktop connection

The optional **Connect local Codex** control works in the wallet's current browser, without asking that browser to share its wallet extension or signed-in cookies with another app. Download the companion from the collapsed connection panel, open a terminal in the download folder, run `node polkaswap-codex-companion.mjs` with Node 26 and an already signed-in Codex CLI, and paste the one-time pairing code printed in that terminal. If a browser agent connects before the companion is paired, the collapsed local pairing control remains available on the goal form. The page makes no loopback request until **Pair Codex** is pressed. It sends only the prepared public training context to `http://127.0.0.1:39847`, receives one bounded draft batch, and submits it through the same expiring mailbox and strategy validator as manual site tools. A fixed `draft_failed` model response gets one automatic retry with the same training context if at least 30 seconds remain; authentication, rate limits, transport failures, timeouts and malformed responses do not. Manual Retry remains available if the second attempt fails. Pairing grants no funding, signing or execution permission. The bearer stays in page memory and is erased on disconnect or page exit; neither code nor bearer is placed in a URL, browser log or browser storage. A stopped or unresponsive companion leaves the manual assistant controls available. Re-pair using the current terminal code if the bearer expires. No provider API key is used.

A hard reload or navigation away from the simple flow ends the desktop handoff and erases the local companion bearer. The unsigned watch remains paused until the user explicitly presses **Resume watching**. Desktop recovery requires reconnecting the assistant to the new page session and pairing the companion again if used; a hard reload also requires API users to re-enter their provider credential. The tab-scoped watch checkpoint contains no bearer or signing material.

The desktop path uses [site tools](https://learn.chatgpt.com/docs/webmcp) when exposed by the current browser connection. The desktop app handles its own [account authentication](https://learn.chatgpt.com/docs/auth); Polkaswap neither reads its login credentials nor converts a subscription into an API key. Keep the same Polkaswap tab and browser profile attached to the desktop task. The public catalogue for this connection is:

| Tool                          | Purpose                                                                                |
| ----------------------------- | -------------------------------------------------------------------------------------- |
| `polkaswap_autopilot_connect` | Acknowledge the current connection ID; grants no wallet authority.                     |
| `polkaswap_autopilot_status`  | Read connection, drafting, research and review progress without revealing wallet data. |
| `polkaswap_autopilot_context` | Read only the pending public training context after acknowledgment.                    |
| `polkaswap_autopilot_draft`   | Validate 1–3 distinct strategies in one matching draft and resume local research.      |

**Assistant controls** uses the same handlers, validation, expiry and cancellation as these tools. It works through normal browser interaction when WebMCP is absent. The public context is a visible, read-only text field. Long requests use pages of at most 6,000 UTF-16 units so native accessibility can read the entire request without clipboard access. Read every numbered page with Previous/Next and concatenate their text in order to recover the exact JSON, including all training candles and the trailing response schema. Request changes reset the view to its first page. **Copy instructions** and site tools still provide the complete original request. Response submission accepts bounded JSON, never executable code. The manual path requires no local server or hosted relay.

An ordinary browser cannot detect another open desktop application or acquire its signed-in session. WebMCP support varies independently of browser-extension access: a connected Chrome extension may offer ordinary browser controls without advertising site tools. The UI therefore does not require WebMCP or redirect to another browser. Late registrar injection is detected without reloading this tab. Registering tools does not send a task or verify a signed-in account. **Agent connected to this tab** means a matching session acknowledgment was received, not verified identity or a promise that the assistant stays online. A new connection ID invalidates a previous handoff. After the reviewed session is authorized, local deterministic execution does not need repeated desktop messages.

Each desktop draft request expires after five minutes and can be consumed once. A mismatched, expired or reused request ID cannot resume research. A request deadline reports the existing task-expired message rather than incorrectly claiming that market history is stale; **GO** prepares a fresh request with the retained budget and pair. Timer, status-read and late-submission expiry use the same explanation. Cancellation and disconnect revoke pending work; disconnect also removes the registered tools.

After a draft is consumed, status follows the local workflow instead of returning to `awaiting_budget`: `researching`, `watching`, `awaiting_review`, or `research_failed`. A failure exposes only its sanitized message key and bounded qualification stage/reason codes. No validation observations, returns, prices, wallet data or provider text are included. A failed holdout ends that run; these diagnostics do not authorize tuning against the same reserved period. `bot_available` means the page has a saved bot, not that its signer is unlocked, it is running, or it has made money. An invalid or detached progress reader reports `unavailable`. Pending requests retain `awaiting_draft` and their request ID; connection and draft expiry rules still take precedence. Reading status never starts research or trading.

## Waiting for new evidence

When opening, training or validation evidence rejects a submitted GO plan, the page retains its exact budget, pair and risk limits in an unsigned **Watching for an opportunity** state. The editable budget stays visible with the next scheduled check and **Stop watching**. Reasons remain in the collapsed details. There is no funded bot, balance reservation or signing permission while watching. Editing the plan, stopping, disconnecting, changing wallet/network or leaving the page cancels pending checks. Keep the page open for checks to continue.

The collapsed **Last check** label shows “data through” with the verified completed-hour boundary that produced its diagnosis. If an already exposed validation diagnosis is reused, it keeps that older boundary even when a newer history read is attempted. The validation reason codes are stored with that exact reserved holdout window and return after a same-wallet, same-chain watch resumes from a reload. The latest training rejection also returns after an explicit same-tab resume, bound to its original completed hour in the unsigned watch checkpoint. Alongside the already-saved public goal, that rejection adds only allowlisted candidate and quote-screening reason codes, its data hour, and an exact canonical binding to the same public intent; dated fee-pressure figures remain memory-only. If a verified-history check instead fails on the opening-risk bound or an unavailable pre-draft quote, the same-tab checkpoint retains only the allowlisted error key, its original data hour, and the intent binding. Explicit resume restores that dated error without storing opening figures or quote values. If a trusted exact buy fee exceeds the selected reserve, the unsigned watch retains a dated **Last check** with only the allowlisted fee-budget error key, verified hour and same-goal binding. It checks again only when the next verified hourly window becomes eligible. After a same-tab reload, it stays paused until the same wallet, chain and assistant reconnect and the user explicitly resumes watching; the failed hour is never retried. Editing the goal or pressing Stop discards the record. The binding prevents accidental cross-goal display, not malicious same-origin storage edits. Claiming a newer hour keeps the previous diagnosis with its old date until a new trusted result replaces it, or a successful review clears the watch. Neither record contains prices, returns, provider text or credentials. A newer validation reservation replaces its old diagnosis. Without a verified boundary, the label shows no time; the separate next-check time is only a schedule, not a result timestamp. A new GO goal clears the prior diagnosis and boundary from the current view.

A hard reload in the same tab can recover the unsigned watch setup from a tab-scoped checkpoint. Recovery shows **Watch paused**; it does not restart polling or send a request. The checkpoint remains paused while the wallet and node settle, even if they briefly report a different identity during reconnection. Reconnect the desktop assistant or re-enter the API provider credential, then explicitly press **Resume watching**. Resume requires the same wallet address and source and the same chain genesis; it adopts the settled endpoint and runtime version when rearming, then stops an active watch if that full connection identity changes again. A different wallet or chain cannot resume the checkpoint. The checkpoint stores no signer, companion bearer or provider credential, so it cannot restore trading authority. After explicit resume, a past-due watch checks current indexer readiness once and may research only the newest eligible completed window. It never replays each missed hour or repeats an hour durably claimed before an interrupted request. The IndexedDB validation-exposure watermark is keyed to the chain and asset pair, including migration of older endpoint-specific records, so already exposed holdout windows cannot be retried by reload or endpoint change.

Switching to **Advanced**, another Bots workspace, or another app route pauses pending checks and generation while retaining the same valid unsigned watch checkpoint. Return to **AI trading** in the same tab to inspect **Watch paused** and the saved **Last check**. Navigation does not renew the checkpoint's seven-day expiry, change its wallet, chain, goal or limits, or create a checkpoint for an unfinished first research attempt. Desktop tools and companion pairing are removed; reconnect the desktop assistant when used and explicitly press **Resume watching** before any new check. Cancel, **Stop watching**, editing the plan and starting a new goal still discard recovery. Navigation and explicit Resume both recheck the same bounded record, including expiry after an awaited exposure refresh. A malformed, expired, unavailable or replaced checkpoint is not adopted, and a live review or signed bot is never reconstructed from it. Existing trading-session exit and signing rules remain unchanged.

The paused form displays the saved watch's exact public pair, allocation, fee reserve, target and drawdown as read-only values, including while another account is connected or wallet metadata is loading. It shows the original public account address when the checkpoint contains a structured identity, with **Connect account** to reopen the existing wallet selector. The mismatched account cannot resume, submit the saved plan as a new GO goal, or have its balance shown as funding for the original account's plan. The latest retained training reason codes or pre-draft error remain inspectable under their original **Last check** hour before resume; no research runs to reconstruct them. Returning to the matching account and chain restores the explicit Resume action without changing limits, updating diagnostics, or starting research. **Stop watching** discards this saved watch before its form can be edited. Public watch presentation is separate from the identity-gated recovery input; no storage identity is rewritten merely to display it.

An already open watch may also pause when its RPC node briefly disconnects. If the wallet remains connected and that exact same node identity returns, the paired, in-memory assistant rearms the unsigned watch after refreshing durable validation exposure and indexed readiness. A wallet, chain, endpoint, or runtime change requires explicit recovery; a hard reload has no in-memory assistant and never rearms automatically.

Checks use uncached indexer coverage metadata before loading any prices. Only a new completed usable hourly window can trigger another research run, and that run obtains fresh finalized fees. Missing or delayed metadata is retried no more than once per minute after the initial resumed check; missed hours are not replayed individually. Training-only rejection can become eligible after one new completed hour. Before any holdout worker is dispatched, an atomic IndexedDB write records the entire reserved window as consumed, including canceled and failed runs. A later reserved window must start after that exposure watermark, requiring 50 new hourly observations for the current split. The watermark is shared by tabs on this site and survives Stop, input edits, navigation and reload. If that browser storage is unavailable, validation stops before reading the holdout. Clearing site data or using a different browser profile can remove local evidence; this is not a server-side statistical study registry.

Indexer lookups create a fresh descriptor object each time. Retry readiness binds to the descriptor's stable explorer service and its initialized network client, as the history loader does; comparing descriptor objects would reject every poll before issuing a query. Replacing the service or client during a poll invalidates its response.

Watching is research, not trading or a guarantee that an opportunity will occur. A desktop connection is a mailbox: a new request still needs the attached assistant to respond. An expired automatic request or an allowlisted temporary data error preserves the watch and its visible explanation, but that attempted hour cannot be retried automatically. The next new indexed hour can open a fresh request; the page cannot wake an idle desktop assistant. Other provider, configuration and wallet-funding failures stop instead of repeatedly issuing requests. API-connected assistants can answer the new draft directly. Passing fresh research still leads to the ordinary user-controlled funding review and authorization.

When a desktop request expires after history has been verified, **Refresh Codex task** creates a fresh unsigned request immediately for the retained allocation. It reloads and verifies history and current fees, invalidates the expired request, and preserves the validation-exposure watermark. This explicit recovery can reuse an untested hourly window; it cannot retry rejected validation, bypass newer-history requirements, or authorize funding or signing. Automatic checks still require a new completed hour, and Stop remains available.

The existing `netLoss` diagnostic reads “No net gain, or no advantage over holding.” It covers either nonpositive net growth or nonpositive improvement over the unchanged allocation, including equality; a profitable strategy can still fail the holding comparison. The wording does not change qualification or expose which test metric failed. The configured target gain is a live stopping condition; research qualification requires positive net growth and positive excess over idle, not achievement of that target in the backtest.

After a training failure involving drawdown or trade-cost admission, **Why it stopped** may show a compact fee-pressure scenario. The same dated sentence appears in the visible **Watching for an opportunity** status while that evidence is present; reasons for each candidate stay collapsed. It divides one freshly finalized network-fee estimate by the goal's loss allowance at the latest completed hourly pool mark, valuing the full opening allocation including its protected XOR reserve. The hint appears only when the fee would use at least a quarter of that allowance; it labels both the fee-quote time and the older completed-hour pool-mark time, and is omitted if either is stale. It does not debit the wallet, change the limits, prove a strategy impossible or suggest that accepting more loss would create profit. Live funding and signing still require separate review.

The fee-pressure message uses the same four placeholders in every locale: `{time}` for the quote, `{markTime}` for the pool mark, `{share}` for the estimated fee share and `{limit}` for the loss cap. Akkadian (`akk`) remains cuneiform-only. Placeholder and script checks verify catalog consistency, not the linguistic accuracy of all translations.

## Research and execution

`useAutopilot.go()` keeps the submitted setup while awaiting wallet and assistant connection, then starts research once. `autopilot.ts` freezes the market, exact capital, fee budget and goal before requesting history. The simple flow uses `valuationAsset: 'output'`, so strategy comparison and goal progress use the selected output token. It requires a complete recent hourly history, verified denomination, and fresh finalized fee observations. In the simple flow, the assistant chooses a reusable order size below the user’s total spendable capital. A 10 KUSD budget remains 10 KUSD of opening capital with its separate XOR fee reserve; a gross 10 XOR budget with 1 XOR reserved has 9 XOR available for trading. The app observes both directional fees for a partial reference amount before drafting. This reference is a fee sample, not a selected order or a limit on AI sizing. It also quotes the exact quarter- and half-budget sizes. If two available quoted sizes differ on the current first-buy fee reserve or price-impact limit, it quotes one exact integer midpoint as a fourth sample before drafting. For example, a passing 2.5 KUSD buy quote and failing 5 KUSD buy quote add a 3.75 KUSD observation; this proves nothing about intervening or future sizes. An unavailable midpoint remains explicitly unavailable. If the midpoint fails only the price-impact limit, the app may quote one smaller integer midpoint between it and the passing lower sample as a fifth observation. That result applies only to its exact size. Every available sample must still be fresh and finalized when it reaches the assistant. The prompt and typed sizing context distinguish the total allocation, spendable capital and sampled amount; they also supply costs, slippage, the protected reserve, required fill count and partition lengths. The output-token order ceiling matches replay: initial capital divided by the first training close, rounded down at output precision. This ceiling is not inventory; sales require actually acquired output above the remaining fee reserve. After all exact-size probes, a reserve smaller than every available, fresh observed buy network fee fails before drafting; an over-budget reference quote alone does not reject an affordable smaller quote. The assistant receives the dated directional observations for each sample, and each proposed candidate is quoted again at its exact size and cadence. Passing this lower bound does not guarantee adequate funds for a strategy. The AI sees at most 202 observations from the first 70% of that history. Its drafting context contains no future/test observations, validation metrics, account identity or signing material. Jev selects a fixed typed recipe; other supported providers return a validated deterministic strategy. A desktop assistant that submits only one signal gets two additional, fixed long-only rule hypotheses with distinct entry logic. If its submitted size is not among fresh, buy-impact- and buy-fee-passing exact samples, those extra rules use the closest and smallest distinct eligible sampled partial sizes; the seed itself is unchanged. Each candidate gets a fresh exact quote, so an observed sample never guarantees its later quote. Every candidate receives four training episodes; only a risk-passing training winner reaches the unchanged held-out validation once. The fixed hypotheses do not imply a trade or profit and do not change the loss, 1% impact, fee or wallet-approval limits.

Before drafting for a KUSD-to-XOR goal, the assistant also receives an optimistic training-only one-buy screen for each exact sampled size that passes the observed fee and impact limits. It applies that size's finalized network-fee estimate to the best post-funding hourly close in each complete 24-hour training episode and counts episodes that could beat holding. The prompt calls these “24h episodes beating idle”: positive excess over unchanged holdings does not imply an absolute gain in XOR. The screen ignores pool costs, slippage, drawdown and signal timing, so a positive count never qualifies trading. It draws no conclusion about unquoted sizes, multiple fills or held-out observations.

Research displays its current phase as an accessible live status. If price history cannot be loaded or has gaps, the amount, pair and limits remain editable, with the specific error immediately above **GO**. Pressing GO retries preparation using the current form and existing assistant connection; it does not authorize trading. A connection acknowledgment alone is not research success, and incomplete data never proceeds to a live review.

The app evaluates at most three candidates on the training partition using the existing worker-backed engine. The desktop and paired local Codex paths may submit three distinct deterministic strategies in one request; duplicates that differ only in order size, unused fields, decimal spelling, or condition order are rejected. If an authored order size cannot be quoted or its exact first-buy quote exceeds the fee-reserve or price-impact limit, the app tries its largest smaller freshly quoted buy-feasible sample. It keeps the authored signal and cadence, obtains a new exact quote for that adjusted candidate, and drops the candidate if that first-buy quote is unavailable or exceeds a limit. Preliminary screening checks the first buy; replay checks reverse costs on actual proposed sells. Every replayed fill retains its fee, impact, budget, and drawdown gates. If no authored candidate passes training, the collapsed explanation reports how many drafts were submitted and tested, plus bounded quote-screening reasons for original draft positions. When every draft is screened before replay, the primary message says no usable fresh quote was available; it does not claim a backtest failed. It never raises the authored amount or infers costs between sampled sizes. A legacy single-strategy draft retains the bounded order-size search: it keeps the proposed partial amount first, then fills open slots with fresh, independently quoted sample amounts that pass first-buy fee-reserve and price-impact limits. Exact samples nearest the proposal come first; equal-distance samples favor the larger order because fixed fees weigh more heavily on small orders. An unavailable, stale or over-limit sample is never treated as feasible. If fewer than three sizes are available, the app uses the prior half/double hypotheses and quotes each exact amount before replay. Zero, duplicates and full-spendable-capital amounts are excluded. These observations do not establish profitability or guarantee a future quote. Total capital, fee reserve and risk limits cannot increase. Cadence is bounded to whole hours within the goal's 1–24 hour range for authored batches. The 168 hourly observations yield 117 training observations, one excluded boundary observation and 50 validation observations. Each partition is evaluated as independently funded 24-hour episodes, including idle days: four training episodes and two validation episodes, with incomplete trailing observations excluded. Each candidate receives its own exact-notional fee observation; an existing sample can be reused only for the same amount and cadence while still fresh. Every replay checks that observation against its amount and chain identity. Research ranks qualifying training results by mean net return minus maximum episode drawdown, freezes one winner’s complete strategy and fee evidence, and evaluates that winner exactly once on the untouched final partition. Both partitions require complete episode coverage, at least one actual fill across the partition, positive mean net growth and excess over the unchanged allocation in both percentage and token units, and every episode within the selected drawdown limit. A failed holdout ends the run rather than trying other candidates against it. Data and fee identity are rechecked before exposing a live review.

The advanced playground's history loader combines bundled hourly archive observations with the recent indexer tail. If at most 24 hours remain missing, it requests those exact boundaries from the approved public archive. Each recovered observation must have a finalized preceding block and its immediately following block, matching asset metadata and current denomination. This repairs indexer omissions without changing complete-coverage requirements. A true chain halt, incompatible denomination or unavailable archive remains missing; no price is interpolated or carried forward. Repair requests have a bounded lifetime and the connected chain identity is rechecked before caching or using the result.

The saved study retains full-period hypothetical metrics and a separate validated `qualification` record with held-out dates, returns, drawdown, trades and candidate count. The live ledger starts with original capital only. Historical gains and simulated fills never become real balances. The AI generates the strategy during setup; the local engine then executes those fixed rules. It does not silently retune an authorized strategy or claim to have backtested future AI decisions.

The simple flow requests exactly seven completed days (168 hourly closes), independently of the advanced lab's 90-day preset. Its dedicated loader requires verified indexed XOR-pool evidence for the entire requested window, with no archive or USD-price fallback. Before requesting or returning cached history, it checks the timestamp from the same finalized state as the denomination: it must reach the requested closing boundary and meet the existing five-minute live-data horizon (with the same 30-second future-clock tolerance as fees). It repeats this check after fetching. Delayed finality reports the existing stale-market-data message rather than a historical-gap message. It never shifts the window backwards, interpolates prices, relaxes trading freshness, or treats a successful data check as strategy qualification. Real gaps under fresh finality still fail as incomplete history.

Asset candles retain observed open and volume when the indexer corrects a completed close. With valid priced close evidence, chart extrema include that actual close, including its extra precision beyond legacy rounded samples. Missing OHLC or volume still excludes a candle; evidence for a close never repairs an inconsistent original open or invents missing observations.

The simple accumulation flow sets `valuationAsset: 'output'`. Its AI instructions, training ranking, held-out gate, saved study and live goal progress all measure portfolio value in the selected output token. Research converts every equity observation with its corresponding verified pair close before computing return and drawdown; live goals use the fresh observed close and preserve their opening output-token value across resume. The input allocation and fee reserve stay in their original assets until actual approved swaps execute. Output valuation expresses buying power, not a fabricated output-token balance. Existing advanced goals and studies without this field retain input-token valuation.

New simple-flow goals also set `lossMetric: 'drawdown'`, matching the research gate's peak-to-trough loss metric. The live goal keeps a durable `peakValue` independently of the bounded chart history and pauses when observed portfolio value falls by the selected percentage from that peak. Return and the gain target still use immutable opening capital. The compact form and approval review identify this as “below peak.” Goals without the field, or with `lossMetric: 'baseline'`, retain their original opening-value loss rule; existing authorizations are not migrated. A drawdown goal with missing or invalid peak evidence is rejected, and same-epoch storage updates cannot lower its recorded peak. Pausing does not sell holdings or guarantee a loss ceiling between observations.

New research-route GO goals set `targetRequiresIdleOutperformance: true`. The target pauses the bot only after a completed fill in this goal epoch, a gain of at least the selected percentage in output-token portfolio value, and a strictly higher after-cost value than the same opening holdings left untouched at the current observed price. The idle comparison includes the separate XOR fee reserve and starts again from current holdings after an explicit goal reset. The frozen opening allocation and latest idle mark are persisted with goal progress; same-epoch writes cannot replace that allocation, and consent binds it. A fresh observation recomputes both portfolio and idle values before latching; the legacy goal ledger does not retain a canonical market mark that could independently attest a persisted idle value later. Drawdown and expiry still use the full observed portfolio. Goals without the opt-in retain their original target behavior and integrity identities; no older authorization or saved study is silently changed. The separate exact-ledger v1 goal has its own fixed target semantics and needs a versioned protocol change rather than an in-place reinterpretation.

## AI goal and execution-cost inputs

Before requesting fee samples or an AI draft, `autopilot-feasibility.ts` checks the first two verified training observations against the unchanged opening allocation. The replay cannot execute before the second close; a first buy cannot improve its same-price portfolio value before costs, and opening output is absent or protected fee reserve. Unchanged holdings therefore bound the best possible value at that first execution point. If even this cost-free bound exceeds the loss limit, setup returns a local explanation with the observation dates, goal token, bound and limit. It does not propose changing the budget, limit or history window.

This sufficient rejection check uses the same portfolio valuation, 36-place division and strict `>` drawdown comparison as qualification. Equality and amounts that round to equality continue through the normal research path. It handles an included input-token reserve, an output-token reserve and a third-token reserve using its own verified close. It refuses a non-fresh portfolio. It reads no later training values or held-out results to choose the bound; passing it is neither qualification nor evidence of future returns.

Every new GO research request carries the goal's target, loss metric, valuation asset and duration as validated structured fields. The same fields reach native desktop site tools, portable desktop context, Jev and optional provider APIs. The compact prompt describes the task; these fields supply the exact constraints. They include the 24-hour horizon for the default simple goal.

Each current fee observation also retains directional price impact from the quote's `amountWithoutImpact` and actual output. Replays apply pool fees, impact and slippage once each, with directional network fees charged separately. Fresh experiments reject missing or invalid impact evidence; old saved studies without the new fields preserve their original zero-impact assumptions. Advanced results display the new impact assumptions beside the finalized observation time.

AI cost fields identify their finalized block, time, reserve funding and reverse-lot basis. The existing fee sampler quotes the reverse direction using the expected forward output; this differs from the development collector's conservative forward-minimum lot and is explicitly declared. Current quote prices, outputs and minima are excluded from historical drafting inputs. These percentages are a dated current execution-cost scenario, not reconstructed historical liquidity or proof that old trades were executable at those costs. Actual execution still requires a fresh exact-amount quote.

## Session boundaries

The signing session lasts up to 24 hours. Once unlocked, it can continue in a background tab while the browser remains running and awake. Page exit, offline state, expiry, wallet/network changes, Stop, or a scheduler interruption longer than one minute revoke execution and lock the signer. Browser throttling or computer sleep can therefore pause trading. No hosted bot, service worker or server-side key storage is introduced.

Fresh quotes enforce exact per-token amounts, available allocation, slippage, price impact and fees. Goal thresholds pause trades and lock signing; they do not sell holdings, guarantee a maximum loss, or cancel already-submitted transactions. Limits are enforced by the application, not by a separate custody contract. Desktop usage follows the signed-in app's plan and limits; optional provider API usage is billed separately from trading fees.

`useAutopilot.ts` binds each unsigned review to the wallet/network and discards it on cancellation or identity changes. Deposits can outlast the five-minute review window: refreshing balance renews the same tested strategy's unsigned review and clears consent, without silently researching again or authorizing trading. Funding is checked again immediately before starting.

The review shows the selected per-order input amount beside the total budget. The policy's maximum input per swap remains in Trading limits; it is a ceiling, not the order size. Neither figure is a request to exchange the entire allocation at Start.
