# Guided TS Ethereum funding preparation

`useTonswapBridgeFunding` prepares the existing Hashi form for incoming Ethereum mainnet XOR, DAI, ETH or USDT. It does not connect wallets, request a wallet network switch, approve tokens or sign a transaction. `prepareEthereumFunding(symbol)` returns validated asset metadata and an exact denominator, or `null` with a fixed error code. `status === 'ready'` means registration/form preparation is ready; it does not certify liquidity, price impact, wallet balances, funding completion or an acceptable fee quote.

The helper validates the live SORA mainnet genesis, Ethereum chain configuration, canonical Hashi contract, and refreshed asset registration (SORA ID, external contract, decimals and kind). XOR registration requires an Ethereum wallet on the correct network because the existing asset store resolves the canonical bridge's `_sidechainTokens` mapping. XOR's coefficient comes directly from `api.system.getDenominator()` and must be a positive integer; failures never substitute 1. The validated coefficient is stored in the existing bridge state. Existing `calculateBridgeReceivedAmount` divides incoming Ethereum XOR natural units by that coefficient, using `FPNumber`; ERC20 decimals are 18. The coefficient is not hardcoded.

Use `buildTonswapBridgeFundingRoute('DAI')` to navigate to `/bridge?campaign=tonswap&getTs=1&asset=DAI` through the Vue router. `BridgeContainerPage` applies this allowlisted request only at the top-level bridge page, after the shared chain/apps initialization. It retries after the external account/network changes and cancels stale work when leaving. History and transaction routes cannot silently change their transfer asset from this query. Its dedicated `fundingPreparationBlocked` prop blocks the primary transfer/confirm action while preparation is pending or unavailable, while leaving wallet network correction possible. This is separate from the legacy forwarded loading attribute, which the bridge page does not consume.

For a caller staying on the Get TS page, import the composable and call it directly only after the SORA API is ready. Inspect `error` rather than assuming a previous form asset is usable. Cancel pending work when abandoning the route. Do not re-run preparation during an already submitted bridge transaction.

The read-only 25 September 2026 observations in `output/tonswap-growth/ethereum-dai-smart-quotes-2026-09-25.json` demonstrate why live quote/value checks must precede bridging. DAI→XOR supports SMART source selection, but meaningful price impact grows quickly with ticket size. Asset registration is not sufficient to promise a good acquisition route.

Incoming Hashi signing captures the reviewed history recipient, Ethereum sender, network and contract. It rechecks the actual provider account/network before approval, after approval is mined, and inside the submission lock after asynchronous transaction preparation. Changed accounts, networks, contracts or recipients stop the transfer; the destination is never replaced by the current wallet. Approval and transfer requests pin their Ethereum chain and sender. These guards do not revoke an approval that has already been confirmed.

The guided DAI entry also embeds `TonswapLiquidityCheck` for the exact amount currently entered in the bridge form. The result is invalidated by amount, wallet, network, direction, asset or connection changes and by expiry. The policy remains active for the lifetime of that form even if its query is removed, so closing a return guide cannot bypass it. Ordinary bridge sessions retain their existing policy.

Generated guided history records carry `payload.tonswapFunding = 'ethereum-dai-v1'`. The existing public history payload supports this metadata without changing its shared type. Submission-evidence updates preserve unrelated payload entries; retry cleanup removes only `evmSubmission`, and indexer reconciliation spreads the existing local record before applying chain fields. The marker therefore survives retries and recovery. It is navigation policy metadata, not evidence that a purchase or transfer completed.

Before each approval or transfer wallet action, the incoming signer obtains a new DAI/XOR mainnet quote for the persisted exact amount and applies the shared 5% impact and swap-plus-burn fee-coverage rules. This fresh read avoids relying on a UI quote that expired while ERC20 approval was mining. The signer rejects slow/expired quotes, changed history inputs, disconnected/replaced SORA APIs, changed genesis, fees or slippage, and changed Ethereum/SORA accounts. The final check occurs inside the submission lock after transaction preparation. A rejected funding check is translated on the transaction page and can be retried; any approval already confirmed remains on Ethereum.

Focused validation covers form invalidation and query removal, signing quote amount/fee/expiry rules, delayed wallet checks, liquidity deterioration after approval, and preservation of the marker through existing submission/rejection cleanup.
