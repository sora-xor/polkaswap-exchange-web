# Buy XOR funding state and recovery

`/#/buy-xor` shares the reviewed Ethereum → DAI → Hashi → SORA DAI/XOR funding components with Get TS. Its purpose is `xor`; the existing TS campaign defaults to `ts`. Buying XOR ends with verified swap receipt output and wallet review. No burn stage, burn transaction pointer, campaign allocation snapshot, or burn-fee reserve is required for a generic purchase.

Before card checkout opens, an optional `cardDraft` saves exact `deliveredEth` and `conversionEth` inputs in the existing purpose-scoped session plan. The strict parser accepts no status, account, order ID or extra field, requires a positive card budget and positive ETH amounts, and rejects conversion input above the estimated delivery. This is only a navigation hint: after closing/reloading, the user sees neutral continuation/history options, and fresh conversion checks still apply. A fresh card review is an explicit action; changing the original source/budget or tracking the conversion hash removes the hint. It never establishes payment or receipt and does not lock source edits like an unresolved chain transaction.

## API and storage

`GetTsPurpose` is exported from `getTsFlow.ts`. `getTsSteps`, `parseGetTsSource`, `parseGetTsView`, and `resolveGetTsView` take an optional final purpose. `readGetTsView(storage?, purpose?)`, `writeGetTsView(view, storage?, purpose?)`, and `clearGetTsView(storage?, purpose?)` retain their earlier storage argument. Generic parsing rejects `source=xor` and `step=burn`.

`useGetTsPlan(purpose?)` and `useGetTsConversionProgress(purpose?)`, `useGetTsBridgeProgress(purpose?)`, and `useGetTsSwapProgress(purpose?)` accept a Vue `MaybeRefOrGetter<GetTsPurpose>`. The reactive draft slots and session storage keys are separate: `polkaswap:get-ts:{view,plan}:v1` and `polkaswap:buy-xor:{view,plan}:v1`. Plan storage helpers also accept purpose after their existing storage argument. They contain validated amounts, payment asset, submitted public hashes, and an optional bounded reviewed bridge-row pointer; they never persist raw accounts, balances, quotes, secrets or trusted success. Generic plans reject burn references. Purpose changes invalidate pending progress reads, even when references happen to be identical.

## Bridge boundaries

`buildGetTsBridgeRoute('xor')` produces `/bridge?buyXor=1&asset=DAI`. `buildTonswapBridgeFundingRoute(symbol, purpose?)` uses the same purpose contract. The strict query parser rejects mixed TS/generic flags and non-scalar flags. Only explicit guided entry prefills the matching plan's exact DAI amount, once per purpose/asset entry. Ordinary bridge visits do not receive purchase amounts. Changing purpose during asynchronous review cannot associate the unsigned row with the other plan.

A generic reviewed bridge row has `payload.buyXorFunding='ethereum-dai-v1'`. TS retains `payload.tonswapFunding='ethereum-dai-v1'`. Both tags trigger fresh exact-amount liquidity/fee checks before every signing boundary, including ERC20 approval and subsequent transfer; malformed or conflicting tags fail closed. Generic coverage reserves only the swap fee. The guided form retains its selected purpose when its query is removed. History and back links carry only the fixed purpose query; the return notice uses Buy XOR wording and `/buy-xor`, with dismissal clearing only that purpose's navigation hint.

Only the just-reviewed row's actual submitted Ethereum hash is associated with the plan. The pre-submission binding is persisted as `bridgeDraft: { id, amount, contextHash }`; the digest binds purpose, incoming mainnet DAI, amount and both accounts without storing raw wallet addresses in the plan. `useGetTsBridgeDraftTracking` observes that exact saved row on bridge pages and the purchase progress view, so a reload during approval or leaving the detail page before a hash arrives does not lose the binding. The row, amount, current accounts, network, and purpose must all match; duplicate row IDs and arbitrary older history are rejected. The submitted hash replaces the draft binding. Neither the draft pointer nor a hash proves completion: reload revalidates actual receipt/storage evidence with current accounts, chain and purpose. Bridge receipt readers additionally require the history row's tag to match their plan. Existing balances are separate observations and never proof a purchase completed.

## Preserve a purchase while funding is unresolved

`getTsPlanProtection(plan, progress?, preparing?)` is the shared page's pure edit/navigation guard. It protects reviewed bridge/swap drafts and funding hashes unless **every** tracked conversion, bridge and swap has a current verified terminal result for that exact hash. Missing, pending, unavailable, wrong-account and unrelated-reference evidence cannot release it. Verified conversion/swap failures permit an explicit retry or edited plan; a bridge failure remains protected because claim/recovery may still be needed. Burn alone does not lock planning: the burn component continues to own its separate receipt lifecycle.

While protected, the plan screen shows its saved amount read-only and offers the existing resume action. Source/asset/amount changes and balance shortcuts cannot clear transaction associations. Incoming source deep links use the saved payment asset's original source, before any source watcher runs. Action links resume the protected funding stage, including when a user tries returning to an earlier card purchase or conversion; wallet setup remains reachable. Upstream handlers also reject changes after downstream review. Once every funding reference is conclusively resolved, the ordinary explicit plan edits remain available; no completion flag is persisted.

The swap form's `preparing` event and conversion panel's matching `preparing: boolean` event pin the original signing child through local navigation and wallet prerequisite changes before a hash exists. A conversion's valid returned EVM hash is retained before stale-account/provider checks suppress receipt completion. The current-account receipt reader must still verify it; an account change does not fabricate success or borrow the new account's balance. These preparation flags are in memory only. This change does not provide cross-device recovery or guarantee preservation after forcibly closing/reloading the browser during an unresolved wallet request; the existing session/history recovery limits still apply.

## Focused validation

The purpose-isolation suites cover independent storage and reactive slots, malicious burn/source navigation, mixed bridge flags/tags, generic swap-only fee coverage, retained quote policy after query removal, purpose changes during reads, bridge amount prefill, reviewed-draft reload and delayed-hash recovery, modified-row/account rejection, neutral recovery links, current-account finalized evidence and ordinary-flow compatibility. Pending-plan coverage adds blocked source/amount/deep-link edits, exact matching terminal evidence, pre-hash signing/disconnect races, a delayed valid hash after an account switch, upstream-stage navigation, disconnected resume and independent burn behavior. All RPC/wallet providers in tests are mocked; no live financial transaction is used for verification.
