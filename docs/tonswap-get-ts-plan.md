# Get TS draft continuity

`useGetTsPlan()` shares a readonly reactive `plan` across the guided purchase screens. `updatePlan({ paymentAsset, paymentAmount })` sets the original spending intent. Changing either canonical value clears `daiAmount`, `xorAmount`, and transaction associations; downstream amounts should be assigned in a subsequent update. Raw, incomplete text stays in the owning input component. The plan accepts positive natural strings at the payment asset's precision, or an empty string; no token arithmetic uses JavaScript floating point.

The strict v1 record under `polkaswap:get-ts:plan:v1` contains only the payment asset, draft amounts, and at most one submitted transaction hash per conversion/bridge/swap/burn stage. Unknown fields, addresses, success flags, quotes, unsigned history IDs, malformed hashes, excessive precision, and oversized records are rejected. It is tab-scoped session storage, not an order ledger. Storage denial preserves an in-memory draft. `clearPlan()` clears this draft without touching wallet or transaction history.

Use `trackTransaction(stage, hash)` only after the existing financial flow returns an actual submitted transaction hash. A pointer can never establish completion. A newly reviewed guided bridge binds its unsigned local row only in memory; `BridgeTransactionPage` associates its later submitted Ethereum hash with the plan. Changing the original budget clears this binding. Reloading before a hash is observed can lose the association; the independent bridge history remains available.

On the explicit `campaign=tonswap&getTs=1&asset=DAI` bridge entry, the initial exact `plan.daiAmount` is applied once after mainnet registration validation. Ordinary bridge entries are unchanged. This is a reviewable form suggestion, not permission to transfer; existing exact-amount liquidity and signer guards still apply.

`TonswapBurnCampaign` accepts an optional `initialAmount`. It suggests at most the connected wallet's known transferable XOR minus a known positive marked-burn fee. It does not open the review or sign. Subsequent props never replace edited inputs or an open review. The component emits `amount-change` for draft continuity and `submitted: { transactionHash }` for newly submitted local receipts; recovered historical receipts do not masquerade as a new purchase.

## Bridge progress

`useGetTsBridgeProgress()` returns `progress`, `refreshing`, and a read-only async `refresh()`. Progress states are `idle`, `unavailable`, `pending`, `received`, and `failed`; optional details are `reference` (Ethereum hash), `historyId`, `amount`, and `finalizedBlock`. The composable polls every 15 seconds while a tracked hash exists and stops on scope disposal. It never connects a wallet, retries a transaction, or requests signing.

The tracked Ethereum hash must match an incoming Ethereum-mainnet DAI row and both currently connected accounts. The helper then reads one finalized SORA block, resolves the Hashi incoming request, and verifies its Ethereum hash, sender, recipient, asset, exact codec amount and `Done` status before returning `received`. Hashi's SORA storage network ID is 0; Ethereum's EVM chain ID is 1. Persisted history status or a wallet balance alone cannot return `received`. Missing rows, account/network changes, RPC failures, or conflicting data return `unavailable`; this is not proof of failure. A pending bridge with no incoming request mapping remains `pending`. The UI may show existing available funds separately without assigning them to this transaction.

This helper does not inspect an Ethereum receipt when there is no incoming SORA mapping. An Ethereum revert before registration can therefore remain `pending` here; retain the existing bridge-history link for its transaction details and recovery/error handling. `failed` requires matching finalized SORA transfer data with a failed, broken or frozen request status. Account/plan changes discard in-flight reads. Browser state contains neither the result nor the account identities.

Tests cover strict persistence, precision, original-budget invalidation, submitted-reference binding, fee-preserving burn suggestions, edit protection, recovered-history emission exclusion, account/asset/network matching, exact finalized transfer evidence, and asynchronous account/disconnect/RPC changes. No funds are moved during tests.

## Swap progress

`useGetTsSwapProgress()` exposes the same five states, `refreshing`, and `refresh()`, polling every ten seconds for a tracked swap. Its optional details are `reference`, `historyId`, `blockId`, and `xorReceived`. Current-account DAI→XOR wallet history supplies a candidate block only; the saved status never establishes success. An indexed block locator can supersede a local pending row for the same hash.

The reader checks the candidate against the connected mainnet node's finalized height and canonical block hash, locates the exact signed extrinsic, validates its signer and `liquidityProxy.swap` DAI→XOR arguments, then decodes only that extrinsic index's events. `received` requires exactly one `System.ExtrinsicSuccess` and a matching `liquidityProxy.Exchange`; a matching `ExtrinsicFailed` returns `failed`. Unknown or inconsistent evidence returns `unavailable`. This relies on the connected node's canonical-finality attestation, not a standalone cryptographic proof.

When a matching finalized `xorFee.FeeWithdrawn` event is available, `xorReceived` is the exact exchange output minus that observed XOR fee. Omitting the field is preferable to inventing net proceeds. A burn suggestion still leaves the current marked-burn fee available and is checked against the current wallet balance. Preexisting XOR can be an explicit alternative action, but must not turn a pending tracked swap into a completed purchase.

Neither reader searches arbitrary historical blocks for a missing transaction. Swap history must provide the hash and candidate block, and bridge history must provide the matching transfer row. RPC pruning or unavailable historical state can prevent revalidation after a later reload; `unavailable` does not undo a transaction. Current wallet/history links and explicit existing-funds choices remain necessary. These receipt reads rely on the selected mainnet RPC and do not establish guaranteed future liquidity, token delivery, or a TS launch date.

## Ethereum conversion progress

`useGetTsConversionProgress()` returns `progress`, `refreshing`, and read-only `refresh()`, with the same five states and optional `reference`, `amount`, `blockHash` and `blockNumber`. It reads the submitted `plan.references.conversion` immediately, including after a reload, and polls every ten seconds. Each provider request has a fifteen-second timeout. The panel emits the actual submitted hash before waiting for confirmation; a delayed or unavailable receipt remains independently recoverable. No provider method requests connection or signing.

`readGetTsConversionProgress(provider, reference, account, isCurrent)` can also be used by the standalone conversion panel. It verifies Ethereum chain 1 through both provider network metadata and raw chain/account reads; the exact transaction hash and current sender; the allowed conversion gateway destination; matching transaction/receipt block identity; and the receipt's canonical block at a latest height providing at least one confirmation. Account, provider, network, plan or component-disposal changes discard late reads. This is the existing one-confirmation policy, not Ethereum finalized-block assurance: a later reorganization may revoke a previously observed result on refresh.

The successful receipt's canonical Ethereum DAI `Transfer` logs alone determine `amount`. Incoming transfers to the recipient are added and outgoing transfers subtracted in exact integers; self-transfers cancel. Other tokens, other recipients and separate transactions cannot increase this amount. Duplicate log indexes, mismatched transaction/block identities, removed logs, malformed topics/data, nonpositive net output, more than 2,048 logs, overlong log data or uint256 overflow are rejected. The reader never subtracts wallet balances or trusts a persisted completion state. A canonical reverted receipt is failed; a pending or unknown submitted hash is pending; unavailable or inconsistent evidence is unavailable.

The reader covers the on-site Ethereum-to-DAI transaction only. It does not infer completion of an external TON handoff, trace replacement transactions, decode historical provider order state or recover a missing/dropped Ethereum transaction. Receipt reads depend on the selected provider. The independently checked execution adapter remains responsible for the quote, allowance, calldata and gas policy before submission; only a real submitted hash should be associated with this draft.
