# Strategy Lab

Open `/#/bots` to compare experiments before creating a bot. The lab is part of the static Vue/Vite/IPFS application. It creates no server, background trading service, or separate wallet.

## Choose and compare

The **Build & compare** workspace starts with the pair, virtual capital, and three compact strategy choices. Loading the page or receiving token metadata never starts a study; the single **Run experiments** button is explicit. Selecting a strategy name previews its animated lesson; the adjacent selection control includes or excludes it from the batch. The lesson uses labeled example values and generates no market observations or orders. Exact trade sizing uses the capital token’s decimals. Cadence, variations, costs, and validation settings remain editable under **Rules, costs & validation**. The **Inspect a strategy** tab exposes detailed individual research, and **My Bots** manages paper/live sessions.

Choose the input token and the token to acquire independently. The selectors read the complete whitelist and retain tokens whose current finalized XOR pool contains more than one XOR and a positive target reserve; XOR is included as the base token. Discovery uses exact chain reserve units and refreshes every 30 seconds, including tokens outside the SDK’s common-asset set. **Reverse pair** swaps both selections together; an identical input and output is invalid. Up to four output tokens can be researched against the same input token. Every result records its own directed pair and uses prices and fee observations for that pair.

The finalized-head, state metadata, denomination and pool-reserve reads share a 15-second deadline after the whitelist loads. A stalled RPC ends that attempt with the existing stale-data error so workspace initialization and its public-data retry timer can continue. Late replies are discarded and cannot supply token eligibility; no static token fallback replaces the finalized evidence.

Choose scheduled accumulation, price thresholds, moving-average crossings, or a combination. One or three visible parameter configurations per family produces a preview of the exact batch size, up to 36 experiments. Capital, per-trade amount, cooldown in blocks, slippage, XOR reserve, and chronological validation settings remain editable before starting. The quick preview defaults to one-hour buying, matching the hourly observations; comparison settings retain explicit 1/5/10-block and whole-hour choices. Old saved settings that specify only hours preserve that exact interval. Historical tests use hourly observations and cannot validate timing within the hour. Three-variation scheduled-buy sweeps use distinct whole-hour intervals (rounded base, 2× and 4×), visibly disclosed in the builder. Editing the builder does not modify earlier runs.

Three experiments can be animated side by side. Starting a run brings its actual outcome distributions into view, above validation, equity comparisons, and the results table. That order stays stable when calculations complete. Each processing lane shows its actual processed timestamp and equity as historical calculations complete. The comparison table and cards show full-period return, latest held-out return, maximum drawdown, and holding the original starting assets (including the unchanged XOR fee reserve). This holding benchmark does not buy the traded token. Test dates, observation counts and coverage remain visible. The default comparison scope restricts the table, chart and cards to the selected market, chain identity and matching observation timestamps; all saved studies remain available through an explicit broader view. Before the selected result is complete, matching mode shows only the current batch or selected incomplete study; failed studies never expose unrelated old results as matching. Holdout and walk-forward periods are independent test portfolios; the latest held-out return is not an aggregate or a forecast. The detailed evidence includes each fold, the observation range, coverage, and directional fee calibration.

Shortlist identifiers are stored locally for convenient comparison. Duplicating a preset study loads its settings into the builder; duplicating a reviewed generated strategy queues the same exact rule with a new study identity. **Cancel remaining** cancels pending computation. Completed calculations freeze for inspection without an automatic replay. These actions do not authorize or stop an independently running bot.

## Visible strategy library

One twelve-choice picker appears immediately after the token pair and amount, before Run. All nine composable recipes and three basic presets have the same visual treatment; there is no second picker lower on the page. Spring rebound, trend confirmation, range breakout, dip recovery, quiet-market breakout, persistent trend, range recovery, trend pullback, and quiet expansion show the selected idea directly beneath the picker before Run. Choosing a recipe shows its editable buy/sell rules and animation in the customization area, using the existing 18 condition types. Each buy/sell group explicitly matches **All** or **Any** conditions. Both Run buttons (at the first controls and beside the selected strategy) freeze one exact composition per selected market, with automatic tuning disabled and a minimum one-hour cadence. The simple preset comparison remains available.

The animated explanation evaluates the selected formula over clearly labeled example observations. Selecting a condition shows its value and comparison threshold on an axis separate from price. In a completed study, **Replay these rules on the recorded prices** uses the actual historical tail. Signals still require allocation, cost, cooldown and order-limit checks. A sell signal takes precedence when both groups match; repeated qualifying observations can propose additional fixed-amount orders. No exit group means accumulation without automatic selling.

**Share rules** copies a bounded, versioned URL that restores an editable, unexecuted draft under the static IPFS path. It includes only conditions; market, sizing, results, account and execution authority stay out of the link. Duplicating a mixed-rule study opens a detached copy for editing. Paper-bot promotion retains its exact tested conditions, with fresh holdings and execution state.

**Open in Strategy Lab** in Strategy Studio carries a separate versioned public draft: the exact XOR input and selected token address/metadata, signal rules, 10 XOR capital, selected 1/2/3 XOR order size, 2 XOR fee reserve, 0.5% slippage and source archive dates/chain denomination. Lab opens one untuned hourly experiment with a 50% holdout for review; it never runs automatically. Its replay, dataset and freshly observed directional fees differ from Studio, so the resulting returns may differ. Fee observations, results, holdings, wallet state and execution permissions are excluded. Invalid or unsupported drafts and unavailable/mismatched token metadata block running visibly rather than substituting a market. Historical drafts remain shareable; loading history on an explicit run checks the archived chain identity against the current source. Reopening the same Studio link restores its source configuration; normal Lab panel navigation preserves edits, while removing the import resets its draft controls.

See [Composable spot strategies](bot-composable-strategies.md) for exact formulas, archival references, chronological validation, failure cases and performance evidence. The separate AI-assisted composer continues to draft the original three strategy families; mixed rules are edited directly.

## Streaming calculations

`research-runner.ts` processes up to three CPU studies at once and permits two public history/fee loading lanes. The existing history loader caches by its verified chain identity and pair. Each fee request uses the study's exact buy notional and independently observes the reverse direction; the runner rejects pair, notional, genesis-hash, denomination, or freshness mismatches.

`research.worker.ts` receives public asset metadata, deterministic rules, verified historical candles, and explicit fee assumptions. It has no provider key, wallet, signing, or ledger dependency. Web Workers run the same `research.ts` evaluator used by single-strategy research. Unsupported or failed worker initialization falls back to its asynchronous evaluator. The evaluator yields bounded checkpoints at most every 32 decision bars; workers wait for the main thread’s presentation acknowledgement before advancing, and the fallback yields across browser paints.

Progress counts actual decision-bar work in the full study and training/test folds. Each monotonic checkpoint identifies its study/train/test scope, processed and total work, newly evaluated decisions, gate totals, and study-only candidate/trade-marker deltas. Exact partial portfolio metrics, fees, and selected/excluded outcomes come from the evaluator. Partial charts retain at most 128 sampled points; the completed result retains every equity point and candidate. Training progress preserves the full-study metrics instead of substituting an incomparable fold’s portfolio.

Both Strategy Lab and the detailed **Backtesting** tab consume these live checkpoints. Each incoming batch of up to 32 actual decisions updates the outcome histogram. A mounted lane acknowledges its checkpoint after the short measured transition is drawn; the worker then advances. Other lanes remain independent. The distribution receives only evaluated study decisions; training and validation work never substitute a different sample. No replay clock determines the financial counters. Completion, cancellation, or error stops calculation animation immediately, without automatically playing a completed result afterward. Restored completed studies show a static distribution. Hidden, paused, unavailable or reduced-motion renderers settle immediately; cancellation and unmount release pending presentation without stranding a worker. A bounded lost-renderer guard cancels the transition before releasing calculation. Reduced motion changes presentation only.

The lab never generates market prices. Unavailable history, missing denomination evidence, unsupported fee routes, or disconnected current fee queries leave that study unavailable. A pair with a shorter verified history can still be tested: the actual first/last candle and coverage describe the observed period, without requiring a March 1 opening price. Hourly historical candles remain hourly; a six-second live rule does not create sub-hour observations or pretend to test sub-hour fills. Network fees remain current observed costs applied to historical simulations, not a reconstruction of fees at historical blocks. The existing [historical data assumptions](bot-trading.md#historical-data-and-assumptions) still apply.

## Generated rules and bot creation

[Strategy Composer](strategy-composer.md) turns an idea into one reviewed `dca`, `threshold`, or `sma` configuration. It accepts structured data, not executable JavaScript or arbitrary model-written code. The reviewed amount, interval, absolute threshold, direction, and moving-average windows pass unchanged to every chronological validation fold. Parameter optimization is disabled for these exact reviewed configurations.

Keys are never persisted in the research library, saved bot, or application assets. Connecting retrieves the provider’s actual model catalog for selection; generation begins only on the explicit action. The composer revokes its memory-only provider connection when disconnected or disposed. Generating a suggestion does not create a bot or authorize trading.

**Create bot** obtains fresh current fee/chain evidence and verifies that it matches the study's chain and denomination. The parent bot flow obtains a fresh quote and constructs a new idle paper definition. Its initial virtual capital and reviewed rules are preserved; simulated holdings, gains, paid fees, trades, activity, provider credentials, and active sessions are not copied into the execution ledger. The original study and its fee provenance remain a separate research snapshot. Real-money use still follows the existing stop/edit/live/consent workflow in **My Bots**. The handoff focuses the new bot’s heading and brings its idle status and controls into view.

## Persistence and bounds

`experiment-storage.ts` uses the separate IndexedDB database `polkaswap-research-v1` and `experiments` store. It never opens the execution ledger `polkaswap-bots-v1`. Each complete public run has its own record, and a small manifest controls retention; saving a new result does not rewrite previous candle/candidate arrays.

Retention is limited to the newest 36 complete studies and a 48 MB serialized-data budget; a single record is limited to 16 MB. Large histories may therefore retain fewer than 36 studies. Invalid or corrupted cached records are discarded, and incomplete/error runs are not restored as completed research. Storage failure leaves current research available but cannot promise persistence after reload. No keys, real account identity, live allocations, or orders belong in this database.

The UI retains at most three active animation views and, when a new batch starts, the current batch plus up to 36 previous runs in memory. The runner limits each source to the existing 10,000-candle ceiling, terminates workers on cancellation/disposal, and rejects late results from a superseded batch. Fee observations and candidate prices use exact decimal/codec arithmetic; only drawing coordinates and progress fractions use ordinary JavaScript numbers.

## Presentation and integration

The lab follows Polkaswap's light and Noir design-system themes. The lab background uses `--s-color-base-background`, with `--s-color-utility-surface` for secondary surfaces. Text, border, accent, and `--s-shadow-dialog` / `--s-shadow-element` / `--s-shadow-element-pressed` shadows follow the surrounding application; the research views use luminous data marks and tabular numeric text inside that system. Theme controls and reduced-motion behavior remain application-wide. Motion is concentrated in data views, keeping inputs and comparison controls stable.

| Module                                      | Responsibility                                                       |
| ------------------------------------------- | -------------------------------------------------------------------- |
| `StrategyLab.vue`                           | Pair selection, batch controls, comparison, shortlist, and promotion |
| `ExperimentCard.vue`                        | Per-study processed data and live calculation evidence               |
| `ExperimentEquity.vue`                      | Comparable completed equity traces                                   |
| `lab-config.ts`                             | Bounded batch expansion and exact decimal sorting                    |
| `experiments.ts`                            | Study contracts and compact bot provenance                           |
| `research-runner.ts` / `research.worker.ts` | Bounded work, progress, cancellation, and worker lifecycle           |
| `experiment-storage.ts`                     | Independent public research persistence                              |
| `StrategyComposer.vue`                      | Explicit provider connection, review, and proposal emission          |

`ExperimentDefinition` contains `id`, `name`, `ResearchSettings`, and an optional reviewed `StrategyConfig`. `ExperimentRun` adds status, real progress, creation time, result, and fee evidence. `eligible-assets.ts` supplies the complete liquidity-qualified whitelist; `controller.ts` refreshes it and subscribes to finalized blocks for active bot evaluation. The runner calls `onUpdate` with independent snapshots. `createExperimentStorage` provides `list`, `save`, `delete`, `clear`, and `close`. `makeExperimentSnapshot` produces the existing `BotResearchSnapshot` contract for the idle-bot creation path.

## Live cadence and observed coverage

Starting a paper/live bot remains an explicit session action. The in-tab controller evaluates on finalized-block notifications and coalesces notifications that arrive while an evaluation is active; it never runs overlapping fills or catches up missed trades after browser sleep. A one-second maintenance timer reconnects subscriptions and supplies bounded polling if a subscription is unavailable. Whole-block intervals count finalized heights using session-local evaluation/fill markers, so quote latency does not skip an eligible block. A fill anchors its cooldown to the latest observed finalized head. Non-block-aligned saved intervals retain their exact elapsed-time semantics. Actual quote freshness, fee budgets, allocation policy, user pause/stop actions, and finalized settlement still apply. SMA signals continue to use completed hourly closes even when eligibility is checked on every block.

A read-only browser verification on September 14, 2026 found 12 qualifying whitelist tokens, including KUSD. The joined XOR/KUSD source contained 22 supported hourly closes from September 13 17:00 UTC through September 14 14:00 UTC, with current mainnet denomination evidence. Older rows without compatible evidence remained missing. This dated observation proves that the pair can use its available verified period; it is not a claim that every whitelist token has complete March-onward history.

## UX components and motion

The lab uses the surrounding page canvas, a compact heading, and an unboxed data-status line. Strategy controls and result comparisons carry the hierarchy; numbered introductory labels, duplicate result headings, and decorative background gradients are omitted. Secondary actions use the existing translated labels and expose provider requirements in their title.

Result columns expand to use the available width when only one or two experiments are shown. Compact distributions retain their counts, sign colors, descriptive statistics, and historical-results note; repeated methodological explanations sit under **Details**. The histogram and validation report share brighter profit/loss colors in the dark theme for readable contrast.

`StrategyFlow.vue` takes research settings, input/output symbols, input decimals, optional evaluator decision evidence, and `active`/`calculating` flags. Without decision evidence it presents one finite, labeled example: scheduled buys at regular times, price reaching a fixed threshold, or configured moving averages crossing. A playhead pauses at each example event while the rule, balance checks, and trade stages are highlighted. Pause, resume, and replay affect only the lesson. Changing the rule restarts the lesson; ordinary parent updates do not. With evaluator evidence it shows the actual signal timestamp and constraint outcome. Detailed explanations sit under a native disclosure.

`ValidationReport.vue` appears directly below the selected completed distribution. Its optional walkthrough advances through training, locking the rule, and later testing on the same UTC scale as the recorded fold dates. Signed test returns, summary metrics, and sample limitations remain visible. Fold tables, benchmark assumptions, and methodological details are available under **Details**. The walkthrough only emphasizes recorded results; it never changes a research result or suggests a future return.

`experiment-results.ts` formats UTC study/test windows and calculates the unchanged-starting-assets benchmark using `FPNumber`. Result cards emphasize all four metrics equally and call out test windows with no fills. `lab-config.ts` keeps comparison identity and observation matching separate from numerical ranking.

The illustrative lesson, validation walkthrough, and real checkpoint rendering honor reduced motion and document visibility. The lesson also pauses outside the viewport. An inactive detailed-research tab pauses its renderer and bypasses the presentation wait; this does not change calculations. Runtime state in My Bots distinguishes a saved “running” record from an actually active browser session and keeps manual resume and fresh live authorization explicit. Its runtime notice appears in the research views only when bots are actually active.

### Preview placement and playback

The selected strategy's illustrative `RuleFlow` or `StrategyFlow` appears once, immediately above the primary Run action. RuleBuilder receives `showFlow=false` because StrategyLab owns this preview; the standalone default remains true. The secondary Run action follows the customization settings. Invalid rule drafts show an error above Run and in the editor, suppress the preview, and disable both actions.

Illustrations loop over the same observations with a brief hold at the end. Pause, Replay, reduced-motion and lifecycle gates remain available; looping does not fetch history, run research, or trigger trades. Historical decision cards continue to show recorded evidence without an illustrative loop.
