# Exact goal progress

`projectExactGoalProgress` is a read-only projection of a validated, already-funded exact goal. `BotGoalProgress` selects this view only when an exact protocol marker exists. Invalid exact records show an error; they never fall back to a legacy `goalState`. Ordinary bots retain the previous presentation. This does not enable exact goal creation or qualification in the default GO flow.

The main card shows the approved KUSD maximum, recorded XOR value and return, actual network fees, remaining fee reserve, and cumulative KUSD traded. All amounts and ratios use integer arithmetic; tiny nonzero amounts remain visible. Cumulative traded KUSD can exceed the initial allocation after reinvestment, so it is not labelled remaining budget. The recorded pool value includes fees paid at that observation, but is not a current executable exit quote.

`orders` must be a complete local order snapshot. `undefined` means loading and `null` means a failed read. `assertGoalOrderAccounting` verifies the full predeadline and postdeadline receipt correspondence. Pending, missing, corrupt or mismatched evidence withholds mutable financial totals and disables Resume. Proven expired signed orders are resolved without an invented fill or fee. Runtime authority is supplied separately; a saved running flag alone displays paused, and runtime attention remains attention.

After terminal accounting, the value, return and observation timestamp remain the original deadline snapshot. A postdeadline journal changes attributed holdings, total fees, cumulative trades and remaining reserve only. The collapsed “Settled after deadline” section identifies the later fees and trades separately. No new current value, return or price timestamp is invented. Recorded negative values and returns remain visible. Fee overruns and allocation deficits retain attention; the card does not separately display deficit quantities, and attention never receives a positive success color.

`useExactGoalProgress` schedules one display update at the original deadline and clears it on unmount. It performs no market reads, order polling, signing or reconciliation. The Bots page calls the controller's read-only `readGoalOrders` for the displayed exact goal when its saved record or selection changes, and discards stale asynchronous replies. This is a local snapshot, not a wallet balance feed. Runtime and storage remain responsible for writes and reconciliation.

The projection, components, controller and page tests use synthetic accounting and mocked local dependencies. A terminal integration assertion uses actual storage transitions with synthetic canonical blocks, including successful and failed later receipts. No tests contact a market, wallet or external service.
