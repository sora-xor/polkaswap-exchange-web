# Get TS funding journey

The `/get-ts` static route guides the user through source selection, wallet connection, funding, the existing Hashi bridge, the existing SORA swap, and the marked XOR burn. Every financial transaction is reviewed and signed separately. A SORA account is still required: that account signs the burn and owns the future TS claim. TS is not delivered immediately.

## Supported paths

- **Card:** the existing MoonPay integration is restricted to ETH on Ethereum mainnet. The user supplies their displayed Ethereum wallet address to MoonPay; unsigned address prepopulation is deliberately not used. The guided integration disables MoonPay's ordinary automatic ETH bridge preparation. After funding, the user converts ETH to DAI.
- **Ethereum:** quote ETH or canonical Ethereum USDT to canonical DAI through Symbiosis. The adapter permits only the verified Ethereum OnchainGateway and nested 1inch path, checks deployed code and calldata, and requests exact USDT approvals. Approval confirmation can outlive a quote; the user then refreshes before the swap.
- **TON:** connect through TON Connect and quote canonical TON USDT to ETH on Ethereum. Native TON first needs a TON-to-USDT swap. TON cross-chain execution currently opens the provider's app; on-site signing remains disabled pending a complete message verifier and recovery disclosure. After receipt, the page continues with ETH-to-DAI conversion. This is an explicit external step, not an automatic on-site transfer.
- **Existing SORA funds:** start directly from SORA DAI or XOR. The ordinary direct-burn route remains available with its existing policy.

DAI then uses the existing Ethereum-to-SORA Hashi bridge. The campaign query fixes the correct registered asset and validates mainnet metadata before enabling the bridge form. The return notice restores the Get TS bridge stage, including from bridge history. The SORA swap fixes DAI/XOR and uses the existing transaction review. The final burn preserves the exact two-call claim marker protocol.

## Funding checks and transaction boundaries

The read-only SORA liquidity check quotes DAI/XOR using XYK and order-book sources, evaluates price impact with exact fixed-point values, and expires after 30 seconds. The guided purchase and conversion steps require acceptable evidence. The final guided SORA swap separately blocks impact above 5%, including during asynchronous wallet preparation. These checks do not lock liquidity or guarantee a later rate. The ordinary swap and direct burn retain their original policies.

The funding check also requires positive SDK fee estimates for both `Operation.Swap` and `Operation.BurnWithRemark`. These come from `settings.networkFees`, whose wallet subscription refreshes estimates when the live runtime version or fee multiplier changes; the SDK's zero default and missing or malformed fees fail closed. This uses the marked batch-burn estimate, rather than the smaller ordinary burn fee. It assumes the newcomer starts with no XOR to subsidize either transaction.

For fee coverage, quoted XOR is reduced by the accepted 2% upstream conversion bound followed by selected SORA slippage: retained output is `0.98 × (1 − SORA slippage)`. With 0.5% SORA slippage this reserves 2.49% of quoted output. This uses the adapter's worst accepted encoded minimum, even though it requests 1% provider slippage. The reduced amount is rounded down to the 18-decimal chain precision and must strictly exceed the sum of the swap and marked burn fees, leaving at least one codec unit available to burn. The UI displays the fee reserve and conservative remainder; this buffer is a preflight allowance, not a promise about future execution. Changing the intended amount, fee estimates, selected slippage, or SORA connection immediately revokes earlier evidence, including in-flight quotes. Quotes that take longer than their 30-second lifetime are rejected. Each component instance has its own accessible label and heading IDs.

Ethereum and TON gas, provider fees, and later bridge fees must be reviewed separately. The conversion panel displays the native transaction attachment, provider fees, output minimum, destination and impact. It invalidates terms on account, amount, source or TON-network changes. The adapter rechecks mainnet, signer, contract code, gateway fee and calldata before signing. The panel emits the submitted Ethereum hash before waiting so the parent can retain a recovery reference. Completion requires a successful canonical receipt for that exact transaction, current Ethereum mainnet/account context, and positive net canonical DAI Transfer logs credited to the quoted recipient. Unrelated wallet balance changes cannot count as conversion output.

The [TON recovery audit](campaigns/tonswap-2026-09/ton-recovery-audit.md) found a designated recovery signer with strong evidence of a Symbiosis broadcaster role. This delegates recovery authority; it does not establish that refunds go to that signer. Symbiosis documents automatic refunds to the original sender and occasional support intervention. The user's Ethereum wallet cannot initiate the matching ordinary recovery call, and an independent TON rescue path remains unverified. The provider-assisted recovery dependency must be disclosed before enabling on-site TON signing.

MoonPay region, identity, card, and minimum-purchase restrictions remain provider-controlled. No verified embeddable provider currently delivers native SORA2 XOR directly. Do not label card ETH purchases as direct XOR or TS purchases. The optional MoonPay `baseCurrencyAmount` prop prefills a validated positive USD budget with at most two decimals for the locked ETH route, without prefilling an unsigned wallet address. The provider's final amount, limits and fees still require review, and the full intended DAI amount must be checked against current liquidity before payment.

## State and static hosting

Funding estimates now run automatically after a 650 ms input debounce and refresh when their 30-second lifetime ends. An unavailable read retries after 15 seconds. These are read-only requests: they never approve, sign, convert, bridge, or burn funds. The conversion summary shows rounded amounts and one explicit wallet-review action; fee and route mechanics remain available in collapsed details. Exact codec values remain unchanged in validation and execution.

`TonswapConversionPanel` accepts `source`, optional `paymentAsset` (`eth` or `usdt-ethereum`), `paymentAmount`, and a legacy optional `daiIntent` for compatibility. The assisted TON route now derives downstream DAI from a fresh quote of its minimum ETH output, so a missing original plan or an edited TON-USDT amount cannot strand the handoff. Both conversion legs must remain fresh and within the conversion price-impact limit. It emits `update:paymentAsset`, `update:paymentAmount`, an immediate `submitted` result containing `transactionHash`, and a verified `completed` result containing `receivedAsset`, exact natural `amount`, and `transactionHash`. Source, amount, account, provider-chain, or DAI-plan edits revoke the previous terms. A successful submission stops automatic conversion refresh. `readGetTsConversionProgress` verifies the canonical Ethereum transaction/receipt and derives the exact DAI net credit from that receipt alone; pending, failed, unavailable, account-changed, or unmounted results never emit `completed`.

The optional `ethBudget` caps the explicit “Use available ETH after fees” suggestion. This read-only action uses the smaller of the observed wallet balance and the gross budget, obtains an executable half-budget probe quote, and estimates its current gas through the signer without requesting a signature. It retains twice the estimated conversion gas at current fee data, the existing Hashi bridge reserve, and the quoted native provider fee before filling an amount. It rereads the actual balance and account/network context, rejects stale or unavailable evidence, and always requests a fresh full-size quote afterward. Different route sizes can use different gas: this suggestion is conservative planning, and the existing final transaction gas and balance checks remain mandatory. Never copy an entire MoonPay ETH output or wallet balance into a conversion amount without reserves.

The panel emits `phase-change` (`ton` or `ethereum`) initially, on source resets, and before clearing or changing intermediate amounts when the user switches from TON to Ethereum funds. The parent must scope payment-amount updates using this event: the original TON/TON-USDT budget and an intermediate Ethereum amount have different units. Entering the Ethereum phase selects ETH and clears the intermediate amount; it does not claim that a TON transfer completed.

`TonswapLiquidityCheck` accepts optional exact `amount`, `compact`, and `paused` props and emits the same exact `checked` result used at financial boundaries. `compact` hides repeated explanatory controls; `paused` stops new reads during wallet review while preserving accepted evidence only until its original expiry. Both the conversion quote and the liquidity result are captured at the explicit review click. Replacing either, changing the input generation, or allowing either to expire makes the adapter's continuation guard fail. A replacement quote needs a new click, even if its terms improve; there is no automatic retry of a financial action. The TON path remains an explicit provider handoff with on-site execution disabled.

`getTsFlow.ts` stores only the version, source and visible step in tab-scoped session storage. It never persists wallet addresses, quotes, signed data or completed-stage flags. Balances show readiness, not proof of a particular purchase or bridge. Internal links use router locations and work with IPFS hash routing.

`getTsPlan.ts` separately persists the purchase amounts and submitted hashes, scoped to TS or generic Buy XOR. Before the guided bridge opens wallet approval, it also saves a bounded `{ id, amount, contextHash }` pointer to the exact reviewed history row. The digest binds the purpose, incoming DAI asset, Ethereum mainnet, amount, and both accounts without storing raw addresses in the purchase plan. A shared observer on bridge pages and the purchase progress view recovers a real Ethereum hash only from that exact row with the same connected accounts and mainnet context. It never adopts another matching-looking history entry or treats this pointer as completion. Edited budgets or DAI amounts revoke the pointer; a submitted hash replaces it. This restores progress after a reload during approval or after returning before the hash was available. Finalized matching bridge evidence is still required before continuing.

TON Connect is lazy-loaded only after a connection request. Its public manifest is served at `https://polkaswap.io/tonconnect-manifest.json`; provider wallets need to fetch this stable public URL. The manifest contains no credentials. Existing public MoonPay configuration is reused; no provider secret or server-side signer is added to the static build.

The UI strings are merged from `src/features/misc/getTs.en.json`, `getTsFunding.en.json`, and `getTsPreview.en.json` into the authoritative locale catalogs. Unit tests cover quote expiry, changed recipients, network changes, exact amounts, adapter calldata and approvals, bridge preparation/signing guards, fixed-pair swap protection, and navigation state. Browser checks use mocked financial boundaries or read-only production data; no purchase, bridge, swap or burn is performed as QA.

## Locale verification

All locale keys and interpolation placeholders are synchronized. Modern locale additions use the repository translation workflow. Akkadian and Egyptian use the existing script-constrained catalog vocabulary; structural and script checks do not establish human-reviewed linguistic accuracy. These specialized translations need expert review before relying on them for a financial decision.
