# Exact goal application composition

`createGoalApplication({ storage, agent, releases, onChange? })` connects the production wallet balance/signer/Web Locks adapters, owned swap preparation, exact funding service, live executor and finalized-head runtime. The `releases` array is trusted application configuration: `{ id, url, sha256, bundleIndexSha256, certificateSha256 }`. Release URLs end in `/manifest.json`. The array must remain empty until a real qualified release exists. Query parameters, AI replies and imported certificates cannot add an entry or choose an evidence URL.

The application loads a configured release through the fixed `loadGoalQualificationRelease` implementation and retains its owned qualification privately. Release production performs the complete original raw study replay offline before publishing the small pinned certificate artifact. The browser explicitly trusts its shipped release pins; it does not pretend to replay omitted raw evidence. `reverifyGoalStudyBundle` remains the full raw verifier used by the release pipeline. No fictional release or default pin is supplied here.

The UI sequence is:

1. `prepareQualification(id)` loads the pinned release once per tab. It returns a detached frozen summary with certificate/policy digests, binding, exact lots and policy. It exposes no qualification capability and cannot allocate or sign.
2. `preview({ bundleId: id, draftId, account, source })` reads current transferable balances and an owned finalized context. It returns an owned `GoalApplicationReview` containing the existing funding preview union. A presentation-only UI can use the detached summary and preview without writing a bot or a funding epoch.
3. After the user approves the displayed allocation, `approveFunding(review)` creates or restores the matching exact goal in **paused** state. The budget is exactly 10 KUSD with a separate 1 XOR fee reserve, and the qualified fixed trade lots are never scaled. Preserve `draftId` for allocation retries so storage uniqueness prevents a second epoch; already stored goals use the separate existing-goal review described below.
4. Pass the returned bot to the controller's existing explicit Start flow, which uses `application.runtime`. Existing unlock/trading approval remains required. Approving funding never calls Start or opens a signer.

The original review object is single-use and expires after 30 seconds. A new preview for the same account/draft supersedes its old review. Copied, mutated, cancelled or stale reviews cannot approve. `discardReview(review)` revokes only that pending review; it leaves qualification and approved sessions intact. Retrying an allocation uses a fresh preview with the same draft ID. Current wallet/account/source, client object, observed identity epoch and review version are checked inside funding's own context/storage guard, including after asynchronous balance reads. Changing wallet/source revokes the approved runtime association; returning to the previous source requires a new reviewed allocation confirmation. Review cancellation during approval prevents a later initialization, but cannot roll back an allocation already committed before cancellation; that record remains paused and resumable.

The runtime uses the original exact goal deadline, actual indexed completed-hour evidence and the captured SDK client's finalized-head subscription. Its `isCurrent` check includes the approved wallet **source**, account and network, in addition to the runtime/live executors' original client, runtime, metadata and consent checks. Allocation and execution use the unchanged `polkaswap-bot:<network>:<account>` Web Locks namespace. Exporting `createBotLiveDependencies` only exposes the existing application adapter factory; legacy behavior and signer implementations are unchanged.

`dispose()` aborts pending release reads, revokes retained qualification, invalidates reviews, stops the runtime, locks its live signers and removes the status subscription. It never closes the shared wallet/RPC client. The controller can use `runtime.dispose` as the same whole-application cleanup hook. This registry is application plumbing, not protection from arbitrary same-origin JavaScript.

The measured failed training acquisition explains why raw replay is outside the public GO hot path: a filesystem-stat-only audit counted 69,135 training files totaling 511,539,857 bytes across eight episodes. Its approved metadata inventory lists another 12,235 files totaling 2,008,571,422 bytes. These figures exclude validation and other parent/journal overhead, and the verifier may consume a subset of metadata; they are archive sizes, not a claim about an exact future compressed network transfer. The small release artifact moves full replay to the release process without granting authority to an arbitrary JSON certificate.

Focused integration tests use real exact funding/storage and genuine synthetic qualification ownership, with mocked release transport, current chain contexts and execution orchestration. They verify read-only previews, exact amounts/reserve, one paused epoch, shared lease keys, explicit Start, private/cancelled/stale reviews, source changes, cancellation during approval, disposal and concrete adapter wiring. No live network, wallet, real study or validation observations are used.

The default `useBotTrading` creates this application only when `GOAL_APPLICATION_RELEASES` in `goal-config.ts` is nonempty. That compiled list currently contains **no releases**. When configured, GO recognizes exactly 10 KUSD into XOR, a separate 1 XOR reserve, and 5% target/loss limits. It uses the existing review component, showing a detached unsaved `BotDefinition` with no execution marker, exact ledger or synthetic goal progress. The controller privately retains the owned review. Explicit Start calls exact funding approval, then the existing controller Start with the user's current unlock/consent; it never calls legacy `saveLiveBot` or legacy authorization for this goal. Cancellation and connection changes discard the owned review, and refresh retains its original draft ID. All other requests and unconfigured flows keep their existing behavior.

Existing goals resume after reload through `previewExisting({ botId, account, source })`, which reads the actual stored paused exact goal and selects only the configured release whose certificate digest matches its original qualification. It returns a detached qualification summary and an owned `GoalApplicationExistingReview` containing the unchanged stored bot and current allocation preview. It has no draft ID. A missing release, wrong wallet, completed goal or original deadline that has elapsed is refused.

After fresh user confirmation, `approveExisting(review)` acquires the same account Web Lock used for execution, verifies the full stored snapshot again (including epoch, ledger, control and signal state), rereads current available funds, then checks that snapshot and wallet/source/client identity again. It grants only the private current-session Start permission. It never calls initialize, save, reset, signer or Start, and does not extend the original deadline. The existing-goal review reads balances and persisted accounting. Current execution-context, metadata and runtime capture happens during the existing live/runtime Start, which independently reconciles pending orders, acquires its execution lease and revalidates current chain/runtime/allocation before unlocking. A changed snapshot, stale or copied review, insufficient funds, cancellation, connection change or disposal prevents approval. Lease waits expire with the original 30-second review; late acquired leases are released.

Controller resume and refresh route this existing-goal review through the same concise review component. Its presentation preserves actual existing holdings, fees, trades and creation time without installing a fake exact execution marker. The controller keeps no persisted draft mapping and never tries to invert a bot ID or consent digest. No compiled release has been added, so these paths remain unavailable until a real qualified release is shipped.

Live history requests use `requiredStrategyCandles` from the existing validated strategy parser, plus one completed-hour publication buffer. A 24-hour trend needs 24 closes and queries 25 hours; restoring(24) needs 26 closes and queries 27; restoring(200) needs 202 and queries 203. The existing SMA bound is 500 closes, so its largest query is 501 hours. This prevents a publication delay from removing the minimum contiguous prior tail and fixes the fixed 201-hour query starving restoring(200). The same goal-signal readiness, gap, boundary and no-carry rules still apply; the signal evaluator itself is unchanged. Old archive manifests, 200-hour warmup contracts, raw replay and qualification gates remain unchanged.
