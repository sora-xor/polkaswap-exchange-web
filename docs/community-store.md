The following is an internal launch calculation for operators, not storefront copy: convert JPY 1,500 once using the September 25 MUFG snapshot and the internal USD 5.37 per XOR value.

```
XOR per bag = ceil_to_6_decimals(1500 / JPY_per_USD / 5.37)
```

The September 25, 2026 MUFG snapshot publishes USD TTS 159.78 and TTB 157.78 at 10:26 JST. The store derives their midpoint, 158.78 JPY/USD; it is not represented as a separately bank-published TTM quote. This gives 1.759225 XOR per bag. Shipping was separately converted upward to six decimals once, then frozen in the published XOR rate table. All codec math is integer-based; the Polkaswap adapter validates its exact `FPNumber` codec reconstruction. The native chain denominator is checked for changes, not applied as bridge conversion.

## Static integration

`public/community-store.json` pins merchant identity, recipient and relay URL. A null relay URL is the intentional prelaunch state: browsing works and new payments are disabled. Configure the HTTPS relay URL only after it is operational. Relative assets and hash routing work under an IPFS path prefix.

For a private local rehearsal, first start the separately configured customer-only relay proxy on `127.0.0.1:39849`, allowing the exact frontend origin `http://127.0.0.1:41829`. Then run:

```sh
PS_STORE_REHEARSAL_RELAY_URL=http://127.0.0.1:39849 yarn vite --mode store-rehearsal
```

Open `http://127.0.0.1:41829/#/store`. The rehearsal Vite plugin fixes that loopback host and port with `strictPort`, disables HMR and all filesystem watching (`server.watch:null`) to preserve a prepared checkout, and overrides the development responses for `/community-store.json` and `/env.dev.json`. Dependency discovery starts only at the app's `index.html`, so archived sites under `output/` and `artifacts/` are not scanned. Merchant identity, recipient and every other store field come from the unchanged public file. In this explicit rehearsal mode, `/env.dev.json` serves the exact bytes of `public/env.json`, preserving the production mainnet settings without changing either file or the app's `DEV` flag. The source must pin SORA mainnet, use MOF as its first node, and contain only the existing MOF mainnet endpoints. The runtime URL accepts no query or the exact `v` build-version query used by the app; other queries are rejected. Changes to rehearsal files require a deliberate server restart after preserving or clearing any prepared order. Normal development retains its usual watching/HMR and testnet settings. Existing loopback validation and wallet signing guards remain in place; no pricing rules change. The plugin refuses missing/non-loopback relay URLs, preview, production mode, and builds with rehearsal mode or its environment variable present. Ordinary builds do not read or emit the override. Stop the local server and unset the environment variable after rehearsal; this does not enable public checkout or install a proxy.

Source responsibilities:

- `src/features/store/client.ts`: validate relay data against pinned chain/asset/merchant policy; quote exact native amounts; carry private capabilities in headers.
- `useCommunityStore.ts`: save private orders, recover a lost create response, preserve frozen instructions, poll status and mount payment only after order persistence.
- `walletAdapter.ts`: fresh account/chain/denomination/balance checks, constrained `liquidityProxy.xorlessTransfer`, fee estimate and durable relay signing lease.
- `pages/StorePage.vue`: product, delivery form, private recovery receipt and fulfillment status.

Only a random public reference is attached to the transfer. Names, addresses, contact details and recovery tokens never enter transfer comments, public URLs or IPFS assets. This tab's session storage contains recovery capabilities only; saving the receipt enables recovery after the tab is closed. Treat that receipt as private. The relay encrypts order records, uses protected operator access and encrypted backups, and holds no spending keys. See the Sora Pay operator runbook for retention and backups.

The browser's transaction hash is only a hint. Finalized successful on-chain evidence establishes payment. Ambiguous signing/broadcast outcomes keep the payment pending; a second attempt is not automatically enabled. Outbox persistence is atomic with payment acceptance, and delivery failures retry without asking the customer to pay again. Acknowledgments/tracking to customers are handled by the fulfillment owner using the chosen contact method.

The MOF node retains only 256 blocks of historical state. The Polkaswap configuration uses the existing approved OVH archive at `wss://mof2.sora.org` for missing historical state, preserving `wss://ws.mof.sora.org` as primary. Its block identity must agree with the primary finalized chain; unavailable or inconsistent history pauses new checkout without skipping the persisted scan cursor. A transaction hash from a customer is not a substitute for missing finalized history.
