# Amount-first Get TS preview

`GetTsPlanPreview.vue` owns only public indicative reads. The parent supplies `source`, `amount`, and optional `paymentAsset`, handles `update:amount` / `update:paymentAsset`, and receives `preview: GetTsPlanPreviewResult`. Mount it on the source screen; retain results in memory only, and treat `expiresAt` as mandatory. The preview contains no addresses, calldata, signing state or executable quote. A new wallet-specific review is required before every actual action.

The optional `purpose: 'ts' | 'xor'` defaults to `ts` in the preview, conversion panel, and liquidity check. Generic XOR purchases return `spendableXor` after the estimated swap fee and conservative conversion/slippage buffer, with no burn fee, TS estimate, campaign cap, or indexer request. The campaign snapshot and reward module are loaded only for `ts`. Existing XOR entered with `purpose: 'xor'` is reported unchanged because no swap or burn transaction is proposed. Both purposes retain the same mainnet verification, expiry, provider validation, gas qualification, and 5% price-impact limit. A purpose change immediately revokes prior preview and funding evidence.

`evaluateTonswapLiquidity(amount, xorCodec, withoutImpactCodec, fees, now?, purpose?)` accepts purpose as its final optional argument. TS results expose `burnableXor`; generic results expose `spendableXor`. The generic conservative calculation is `quoted XOR × 0.98 × (1 − SORA slippage / 100)`, rounded down to 18 decimals, minus the current positive swap-fee estimate. It must leave at least one codec unit. A missing burn estimate cannot block a generic purchase; a missing swap estimate still does. `SORA_FUNDING_MAINNET_GENESIS` is a shared campaign-independent chain constant for these funding checks.

- Sources map to exact networks: card USD → native Ethereum ETH; Ethereum ETH/USDT/DAI → Ethereum DAI; TON USDT → Ethereum ETH → DAI through a provider handoff; existing SORA DAI → XOR; existing SORA XOR → marked burn. Native TON returns a clear unsupported direct-quote state.
- Public reads debounce 650 ms. An edit, fee change, disconnection or expiry immediately revokes the previous result. Successful reads refresh after at most 30 seconds. Failure offers retry. Aborted/late requests cannot replace newer evidence.
- `daiAmount` is expected DAI and `daiIntent` is the provider's minimum DAI or entered DAI. `paymentEthAmount` is card-provider estimated ETH delivered, **not ETH available to convert after gas**. `providerMinimumUsd` is an upward-clamped provider total that exceeded the entered budget.
- SORA mainnet genesis is verified before/after reading. Current positive SDK fees are required; default zero means unknown. DAI/XOR uses the same SMART RPC sources and conservative conversion/slippage allowance as the funding preflight. XOR input is a total budget and its marked burn fee is subtracted first.
- Reward estimation uses the fresh, finalized, marker-validated complete global burn snapshot and the exact integrated campaign curve. Missing totals do not become zero. Capacity excess and price impact above 5% block the proposed amount.
- `costCoverage: partial` applies to card/Ethereum/TON. Conversion and bridge gas require ETH; TON also requires TON gas. The amount input is labeled “You pay,” and card budgets explicitly include provider fees. The dominant token estimate is qualified as before gas, with a short visible “Remaining costs” explanation. TON explicitly identifies both gas currencies. Full ETH-delivery, DAI-conversion, provider-fee, SORA-fee and calculation explanations remain in closed route details. The same-budget eventual output will be lower when purchased ETH funds gas. No fixed gas amount or fee-free route is invented.
- A provider minimum is offered as an explicit budget edit. Price-impact/cap failures offer `findGetTsAmountSuggestion`: at most six sequential, cancellable fresh route estimates, reducing exact fixed-point amounts and checking a provider minimum if encountered. The result is a usable example, not a maximum or a reserved price. Selecting it edits the amount and triggers the normal complete preview again. No budget is changed automatically, no extra transactions are split or submitted, and stale/context-mismatched results are discarded.

## Provider evidence

[MoonPay real-time buy quote](https://dev.moonpay.com/api-reference/widget/getbuyquote) documents the public-key GET `/v3/currencies/eth/buy_quote`, `baseCurrencyCode`, `baseCurrencyAmount`, `paymentMethod`, and `areFeesIncluded`. The existing production publishable key returned HTTP 200 with CORS for `https://polkaswap.io` during a read-only probe. No buyer data or wallet address was sent. `areFeesIncluded=true` requests a total budget. The API may clamp a below-minimum budget upward, so the helper rejects `totalAmount > input`; verifies native Ethereum chain 1; validates provider fee addition; and preserves monetary JSON lexemes before fixed-point parsing.

[MoonPay widget parameters](https://dev.moonpay.com/widget/on-ramp/customization/parameters) document budget prefill independently of the mandatory server signature when passing `walletAddress`. This component does not prefill an address or sign a URL. Card eligibility, region, final fees and rate are still determined by the provider.

[Symbiosis API](https://docs.symbiosis.finance/developer-tools/symbiosis-api) quote requests require source and destination addresses. For indicative reads only, the existing strict conversion adapter receives fixed public dummy accounts. The returned transaction is immediately discarded; only validated output/minimum amounts, fees, impact and expiry reach the preview. No user address or secret is read. TON minimum output is used as the next Ethereum conversion input.

English additions are in `src/features/misc/getTsPreview.en.json`; the integrating task must merge them into all supported catalogs. Tests cover precise reward/fee math, provider budget clamping and network checks, unknown evidence, capacity, stale results, automatic refresh, and input revocation.

The cost-summary presentation preserves the original fixed-point result and all feasibility gates. Component regressions verify that the public gas exclusion stays visible, detailed costs remain in the disclosure, native TON's gas requirements are distinct, SORA-only estimates receive no false extra-gas warning, and future TS claims are not described as delivered tokens.

## Localization validation limits

The integrating update preserves existing catalog values outside the Get TS delta and checks key parity, interpolation tokens, financial-symbol spelling, and required scripts. Ordinary new translations are machine-assisted and should receive a native-language review. The repository's existing `semantic-locales.ts` workflow for `akk`, `egy`, and `pis` uses dictionary and fallback words; passing script tests does **not** establish faithful financial meaning. Those specialized additions need expert semantic review before relying on them as financial instructions.
