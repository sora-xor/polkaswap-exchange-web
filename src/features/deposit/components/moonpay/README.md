# MoonPay purchase dialog

`<Moonpay />` preserves the normal currency-selection flow. A guided ETH funding step can use `<Moonpay currency-code="eth" />` to lock MoonPay to native ETH on Ethereum mainnet. The prop accepts only the exact `eth` code; other values produce no widget URL rather than falling back to an unrestricted purchase. A visible provider checkout is not reset by a budget, language, or theme change. A changed budget invalidates completion for that checkout; closing it rebuilds the widget for the new budget.

MoonPay's `currencyCode` locks the asset, whereas `defaultCurrencyCode` would allow a different selection. The public currency API maps `eth` to Ethereum chain ID `1`; do not substitute a wrapped token or an L2's ETH code. The production widget uses the existing configured publishable key through `initMoonpayApi()`, and the ordinary transaction polling, purchase history, notification, and bridge-confirmation flow remain in use.

Pass an optional `:base-currency-amount="usdBudget"` alongside `currency-code="eth"` to preserve a planned USD budget. The prop must be a canonical positive decimal string with at most two decimal places and 32 characters; zero, signed/exponent/whitespace input, excess precision, and supplying it without the ETH lock produce no widget URL. The widget receives the unchanged string as `baseCurrencyAmount` with `baseCurrencyCode: 'usd'` and `lockAmount: true`. The guided widget also selects `credit_debit_card` to match the public preview's payment method. These parameters do not guarantee availability, minimum, or ETH output; the customer still reviews provider terms. Closing and reopening the same budget preserves its checkout, while editing a closed checkout's budget retires its polling context and rebuilds the URL. Equivalent budgets such as `25` and `25.00` retain the same context. No wallet address or signature parameter is added.

No destination address is prefilled. MoonPay requires a server-side signature for `walletAddress` or `walletAddresses`, and this static app does not have a signing endpoint. The guided page must show the connected Ethereum account with a copy control and ask the customer to paste that address into MoonPay's destination step. Do not paste a SORA address there. The existing bridge flow checks that the purchased funds' recipient matches the connected Ethereum wallet before preparing a bridge transfer. Leave ETH for Ethereum gas and XOR for the eventual SORA burn fee.

A configured public key is not proof of a working card checkout. Payment methods, limits, KYC, and eligibility remain provider-controlled. Current MoonPay documentation also requires signed IP matching for new go-live integrations; production enforcement is enabled per partner account. If the existing widget reports an unverified connection, a missing signature, or another provider error, report that error and require a supported server-side integration. Never expose a secret key in this bundle or bypass the provider's check.

This is a card-to-ETH funding step. Native SORA XOR was absent from MoonPay's public currency catalogs when checked. It must not be described as a direct card-to-XOR purchase; conversion from ETH to DAI, the DAI bridge, and the DAI-to-XOR swap are separate user-approved transactions.

For a guided route, mount `<Moonpay currency-code="eth" :base-currency-amount="usdBudget" :receiving-address="evmAddress" :auto-prepare-bridge="false" @completed="onPurchaseCompleted" />`. `receivingAddress` is used only to match the provider's transaction response; it is never sent in an unsigned widget URL. Guided completion requires native ETH, USD, the exact all-in budget, the current SORA external ID, and the current Ethereum destination. The documented transaction `areFeesIncluded` field determines whether `baseCurrencyAmount` already includes fees or must be added to `feeAmount`, `extraFeeAmount`, and `networkFeeAmount`. Fiat comparisons use integer cents. Missing or incompatible evidence fails closed.

Each opening records a temporary checkout context and the transaction IDs already known. Transactions created before that context, already known transactions, and delayed transactions for a different budget cannot complete it. Changing either account closes and revokes the checkout. Polling startup is serialized so an asynchronously returned polling handle is stopped after account changes or unmount. The store also binds history requests to their captured account, login state, and exact MoonPay API configuration; stale responses cannot replace the current account's history or clear a newer request's loading state.

A matching completed provider transaction closes the dialog, stops polling and emits the complete transaction. It does **not** populate or open an ETH bridge. The parent keeps the received ETH on Ethereum for conversion to DAI first. The default `autoPrepareBridge: true` preserves the existing deposit flow. The event is provider status, not blockchain confirmation or proof of bridge arrival, a swap, or a burn. Provider external IDs are not unique order IDs; history remains available for inspection, and restored navigation hints must not claim a purchase completed.

Validation: 51 component tests cover the budget-reopen regression, visible-checkout preservation, exact completion evidence, account changes, and late polling cleanup. Root integration validation also passed four MoonPay suites (74 tests). These are mocked, no-network tests; no customer-funded purchase was performed.
